# Discovered Findings

Findings that turned up mid-workstream (architecture-remediation, layering-refactor, or any future plan) and were **not** in the originating audit. Per the discovered-findings policy:

- **Critical findings escalate immediately, do not park.** Critical = observable data loss, security issues, observable regressions in shipped behavior, or anything that would block the current release.
- **Everything else parks here** until the next re-audit checkpoint. Don't expand a workstream's scope to absorb new findings.
- **Park the fix, never the verification** (D119). The no-scope-creep rule above governs the *remedy*. Establishing whether the defect is real is not scope creep — it is what makes the entry worth writing. File what is true, not what is plausible: an unverified finding is worse than none, because it occupies the slot and the next reader inherits a guess wearing the costume of a result. If a check is cheap (a grep, a unit test, a run on hardware you already have), run it before filing; DF98 is the worked example of not doing so. If it genuinely isn't cheap, say so explicitly and name the check that would settle it.
- The discoverer makes the severity call; when uncertain, escalate.

## Entry format

```
### DF<N> — <one-line title>

- **Discovered:** <YYYY-MM-DD> · **Workstream:** <W-L1 / W7 / etc>
- **Severity:** CRITICAL / MEDIUM / LOW
- **Disposition:** ESCALATED / PARKED / ADDRESSED-IN-PLACE
- **Description:** <2-4 sentences>
- **Pointer:** <file:line or commit hash>
```

`<N>` comes from **`scripts/next-id.sh DF`**, which scans all four findings sinks *and every local
and remote-tracking ref*, so an ID allocated on a branch that has not merged is still taken. Don't
grep for the highest DF yourself: the sink you forget is where the duplicate comes from, and a
partial grep is worse than none because it also supplies the confidence.

**Entries are in ascending DF order, and a new one goes at the end.** Two reasons, and the second
is the one that pays.

*Navigability*: 45 entries in no order is a file you can only grep, and a misfiled number is
invisible. Enforced by `TestRepoHygiene_AllocationSites_AreInAscendingIDOrder`, because a
convention nothing checks is one that rots (D121) — this file had been both prepended to and
appended to for months before anyone noticed.

*Collision detection*: allocation is inherently check-then-use. `scripts/next-id.sh` tells you 156,
you write the entry, and another PR can take 156 in the meantime — which is exactly what happened
when PR #44 allocated DF153 on its own branch. Nothing closes that window. What ordering does is
make the consequence loud: two PRs that both allocate the same number then insert at the same place
in this file, so the collision surfaces as a **merge conflict** at rebase rather than as a surprise
later.

That is detection, not a guarantee. The guarantee is downstream and unconditional:
`TestRepoHygiene_DecisionCitations_ResolveAndAreUnique` fails `make check` on any duplicate DF
heading, so a collision cannot ship however it arose.

Which is what makes the other path safe: **a finding found and fixed in one stretch of work goes
straight into `findings-resolved.md`**, skipping this file entirely. That is sanctioned and common,
and it does cost the conflict check,
since two PRs allocating the same number into different files will not collide. The duplicate gate
still catches them, one step later. Filing here first purely to move the entry out again buys the
earlier signal and records nothing else.

### DF13 — a swallowed submit key parks the agent on a prompt it never runs (the trust dialog is one cause, not the cause)

> **Title and scope corrected 2026-07-17** (was "Restart prompt re-injection races Claude
> Code's folder-trust dialog (second prompt dropped)"). Two claims in the original are now
> known to be narrower than the defect: it is **not restart-only** — the initial `new` leg
> does it too — and the **trust dialog is not necessary**. Both corrections are evidenced
> below. The mechanism is still **unknown**: 34 controlled trials failed to reproduce it.
> Read the 2026-07-17 evidence before theorising, and especially before re-running the
> approaches already ruled out.

- **Discovered:** 2026-05-31 · **Workstream:** W-L1 (G7, surfaced by smoke run `yoloai-smoketest-20260531-233151.431`)
- **Severity:** LOW — rare (8 of 191 recorded smoke runs) and **loud**: the agent stalls and the caller times out at 90s. No silent corruption. It is a bad failure to *own* rather than a dangerous one: the user's first prompt is silently not run.
- **Disposition:** PARKED — mechanism unreproduced. **Mitigated 2026-07-17, not fixed:** `deliver_prompt` is now closed-loop (confirm the prompt left the input box, re-send the submit key up to 3×, and log `prompt.submit_retry` / `prompt.submit_unconfirmed`). That recovers the observed failure whatever causes it, and turns a silent stall into a named log event — but the race itself is still there, and a retry firing in the wild is the signal that it fired.
- **Re-audited 2026-07-17** against smoke run `yoloai-smoketest-20260717-033706.736` (`stop_start/seatbelt`, commit `a0b4d7c4`, Claude Code v2.1.212):
  - **The signature.** The prompt text sits **composed in the input box, unsubmitted**; context reads `0k/200k (0%)`; `agent-hooks.jsonl` is **0 lines**. So the agent never processed a turn — the text arrived and the submit did not. The input box also carries **trailing blank lines** where the submit keys went, which is what "the Enter became a newline" looks like on screen.
  - **Not restart-only.** This was the initial `new` leg (sentinel `done`, not `done2`). The original's restart framing is an artefact of where it was first seen.
  - **The trust dialog is not necessary**, but *not* for the reason first argued here. The failing snapshot shows no dialog — which proves nothing, because it is captured ~95s in, long after any startup dialog would be gone (that inference was made and retracted the same session). The real evidence is direct: driving Claude Code v2.1.212 by hand, the dialog **does** still appear despite the seeded `hasCompletedOnboarding` + sentinel `lastOnboardingVersion`, and `wait_for_ready` auto-accepts it correctly (it checks `"Enter to confirm"` *before* `ready_pattern`, so the dialog's own `❯` cannot be mistaken for readiness). So the dialog is handled on the path that failed.
  - **Not a regression** from the apple/label-equality work merged at `a0b4d7c4`: `stop_start/seatbelt` passed 4/4 re-runs on that exact commit, and nothing in it touches tmux prompt delivery.
- **Ruled out by experiment 2026-07-17 — do not re-run these.** 34 trials, none reproduced the stall:
  - *Paste→Enter timing gap* — forced both delivery sleeps to 0 (maximally adversarial): **3/3 passed**. Not timing between the paste and the submit key.
  - *Reader starvation coalescing the keys into one paste burst* — 24-32 CPU spinners on 10 cores (load avg 60-98), driving a real Claude Code v2.1.212 through the exact `wait_for_ready` + `deliver_prompt` sequence: **15/15** into a settled REPL and **8/8** against a freshly started one, raw and bracketed alike. Not paste-window absorption in either state.
  - *Load alone via the real harness* — one stall in 2 loaded runs looked like a reproduction; the unfixed control then passed **5/5** under identical load. That first hit was luck, and the A/B cannot distinguish. **Beware:** this is the trap the finding is prone to — a rare flake makes any small sample look causal.
- **A separate, deterministic defect found while investigating this — fixed 2026-07-17, and NOT this bug.** `tmux paste-buffer` without `-p` rewrites every LF to a CR (tmux(1)); Claude Code eats the CR and **joins a multi-line prompt into one line**, so every multi-line prompt on every backend was delivered mangled. Verified by hand: raw joined the lines 3/3, `-p` preserved them 3/3. Claude Code requests bracketed paste (`[?2004h`) and yoloai was ignoring it. All four paste sites now pass `-p`. It is recorded here because it was found here — it is not a candidate mechanism for the swallowed submit, and must not be cited as this row's fix.
- **What would settle it.** The stall has only ever been observed through the full smoke matrix, never in isolation, so the next attempt should instrument rather than theorise: have `deliver_prompt` capture the pane immediately before and after each submit key (and dump the raw pane bytes, not the rendered text), then run the matrix until it trips. The open question is narrow — the text reaches the input box, so input is being accepted; what happens to the key that should send it?
- **Description:** On the `stop_start` restart leg (`restart` → `sb.Restart(StartOptions{Prompt:…})`), Claude Code v2.1.157 shows a "Quick safety check: Is this a project you trust?" dialog at startup whose selector line begins with `❯` — the same readiness pattern the prompt-injection waits for. The relaunched agent reached the welcome screen and sat idle at the ready prompt; the staged second prompt (`prompt.txt` correctly held the `done2` task) was never executed, so `files/done2` was never created and the test timed out (31s gap). Likely mechanism: the injected prompt + Enter is consumed by the trust dialog (Enter confirms "Yes, I trust this folder") rather than delivered to the agent REPL, dropping the task text. Non-deterministic: only podman failed this run (docker recovered on retry; docker-cenhanced/containerd-vm/vmenhanced passed). Matches the known podman network-flake family ("network: unreachable"). **NOT a regression** from the G7 carves — those relocate host-side Go functions and never touch entrypoint, start/restart, or tmux prompt injection (the `StartOptions.Prompt` path is unchanged; only `ResetOptions`/`Reset` were modified). Needs a reproduction before any fix; candidate remedy is to make restart prompt-injection wait for the *post-trust-dialog* steady-state ready prompt (or pre-trust the work copy) rather than the first `❯`.
- **Pointer:** `runtime/monitor/sandbox-setup.py` (`deliver_prompt`, `prompt_pending_in_input` — the closed loop; `wait_for_ready` — the `"Enter to confirm"`-before-`ready_pattern` ordering that makes the dialog safe); `runtime/monitor/tests/test_prompt_submit.py` (the stuck box, built deliberately); `internal/cli/lifecycle/restart.go:74`; autopsies `.testcache/runs/yoloai-smoketest-20260717-033706.736/sandboxes/stop_start/seatbelt/attempt1/FAILURE.md` (the 2026-07-17 re-audit) and `.testcache/runs/yoloai-smoketest-20260531-233151.431/sandboxes/stop_start/podman/attempt1/FAILURE.md` (as first filed).

### DF21 — Docker Desktop containerd store: BuildKit attestations make `yoloai-base` a manifest-list index that vanishes between runs (full rebuild every run)

- **Discovered:** 2026-06-10 · **Workstream:** Apple `container` backend (diagnosing repeated base-image rebuilds during `make smoketest`)
- **Severity:** MEDIUM (no data loss, but a full ~5-minute `yoloai-base` rebuild on *every* operation against a Docker Desktop daemon that uses the containerd image store — increasingly the default)
- **Disposition:** RESOLVED (primary, this commit); the secondary host-global-marker bug remains PARKED.
- **Root cause (confirmed empirically).** `buildBaseImage`/the profile build ran `docker build -t yoloai-base -` with no attestation flags. BuildKit's default provenance/SBOM attestations make the result a **manifest list / image index** on Docker Desktop's containerd image store: the tag points to an index whose platform image has a *different* id. Verified with `docker image ls --tree`: a default build tags an index (`42259e91…` → linux/arm64 `ed62fb1b…`, two different ids), while `--provenance=false --sbom=false` tags a **single image** (`8174802f…`, tag points directly at it). The classic `overlay2` store (OrbStack) flattens to a single image, which is why **OrbStack was unaffected and Docker Desktop rebuilt every run**. The index-wrapped image is lost between runs (containerd-store GC / existence resolution), so `Setup` hit the `!exists` path ("Building base image (first run only)…") on every run. *(Two earlier diagnoses were wrong and corrected: the transient VS Code 404 — a separate flake fixed by `7335018` — and "the SDK can't see containerd-store images" — refuted by a live diagnostic that found the image fine.)*
- **Fix (applied):** both `docker build` invocations in `runtime/docker/build.go` now pass `--provenance=false --sbom=false`, producing a plain single-platform image on both store types — a local base image has no use for SBOM/provenance attestations. **Verify:** re-run `make smoketest`; Docker Desktop should report "Base image built successfully" (skipped) like OrbStack, not "first run only".
- **Remaining (parked, minor):** the staleness marker `.base-image-checksum` is **host-global** (`baseImageChecksumPath` → `CacheDir()`) while images are **per-daemon**. After a Dockerfile change the first daemon to rebuild records the shared marker; a second daemon that already has an image skips `NeedsBuild` (`docker.go:321`) and keeps a **stale** image. Niche (multi-daemon only). Fix: record the build-inputs checksum as an image label read per-daemon.
- **Pointer:** `runtime/docker/build.go` (both `docker build` invocations; `NeedsBuild`/`baseImageChecksumPath`/`RecordBuildChecksum` for the secondary), `runtime/docker/docker.go:309/321` (Setup gate).

### DF28 — Kata guest-readiness race under back-to-back VM churn (`task not found` / exec `ENOENT`)

- **Discovered:** 2026-06-11, verifying DF18's containerd conformance closure on a real Linux+KVM host · **Workstream:** testing-refactor
- **Severity:** LOW as filed (test-infra, non-deterministic). **Recovered from an unmerged branch 2026-08-02** — it was written, never landed, and sat on `testing/backend-conformance` for seven weeks while the same family recurred twice.
- **Disposition:** PARKED
- **Rides:** any.
- **What was seen.** `TestContainerdConformance` and `TestIntegration_ContainerLifecycle` **pass in isolation** but the full suite is flaky: a *random* 2–4 Kata-VM subtests fail per run, and the failing set shifts run to run, so it is not a contract bug in any one subtest. Two signatures, both *beyond* DF8's TC-filter gap: **(a)** the network probe's in-task exec-create races the task becoming addressable — `probe exec create: task <name> not found`, then a 30s timeout, then a follow-on `Exec` seeing `instance not running`; **(b)** interactive/TTY exec reaches the kata-agent before the guest rootfs/PATH is mounted and fails with a Rust kata-agent `ENOENT` backtrace. Every instance boots a full systemd guest and the harness fires create→start→exec immediately, and `task.Start` returns before the guest is ready. FAIL / PASS / FAIL across three full runs on Ubuntu 24.04, kernel 6.8, Kata 3.28.0, containerd v2.2.2, 6 cores.
- **Not resource exhaustion, checked at failure time:** 6.8 GB RAM free, 25 GB disk free, no leftover tasks. The trigger is *concurrency of VM boot and teardown*, which widens the readiness window under CPU contention — the opposite of the smoke disk-pressure case, which shows up as real ENOSPC.
- **Its relationship to the other Kata flakes, stated carefully — an earlier draft of this bullet got it wrong.** It is genuinely the same mechanism as **DF8** (fixed): `task.Start` returning is treated as readiness, and DF8 patched only the network slice of that. [DF159](#df159--exec-start-ttrpc-closed-on-containerd-vmenhanced-during-apply-once-in-38-runs) is a *plausible* relative — an exec into an already-running task dropping — but its exec happens long after start, so shared causation is unproven and it should not be assumed.
  **It is NOT [DF160](#df160--dindpodman-priv-times-out-on-macos-and-the-smoke-harness-turns-a-slow-teardown-into-a-crash), and the dividing line is `sandbox.ready`.** This finding's failures happen *before* the box is ready — the probe cannot exec into a task that is not addressable yet. DF160's recorded evidence is the opposite: `sandbox.ready` at 16–26s on all three cells, then a ~110s gap with no events and `hook.active` never reached. Its own text says so — *"the boot was never the problem"*. A mechanism that fires before readiness cannot explain a stall that begins after it. What the two share is a *symptom profile* — heaviest virtualised cells, flaky under churn, green on retry — and that profile is what made them look like one thing.
- **Fix direction (unchanged).** Gate the first probe/exec on an explicit kata-agent/guest-readiness signal, or serialize VM setup behind a readiness wait, rather than trusting that `task.Start` returned.
- **Pointer:** `runtime/containerd/lifecycle.go` (`waitForNetworkReady`, which emits the `task … not found` probe warning), `runtime/containerd/integration_test.go`, `runtime/runtimetest/conformance_iface.go`. **Paths corrected on recovery** — the original entry cited `internal/runtime/containerd/…`, which the D99 public-layering move retired; the code is the same code.
- **Documented in** [backend-idiosyncrasies.md](../backend-idiosyncrasies.md#kata-guest-readiness-race-under-back-to-back-vm-churn-task-not-found--exec-enoent).

### DF38 — MCP surface has no per-call credential input, and tool-arg injection collides with "agents shouldn't handle credentials"

- **Discovered:** 2026-06-16 · **Workstream:** public-layering (session-layer / trial-engine design, driven by the control-eval consumer — see `design/session-layer.md`, `~/experiments/control-eval/docs/yoloai-trial-engine-report.md` P3)
- **Severity:** MEDIUM (security — credential handling on an unbuilt surface; no shipped regression)
- **Disposition:** **RESOLVED-IN-DESIGN by [D95](../decisions/working-notes.md) ([secure-secrets.md](secure-secrets.md))**; build phased (kept here until built, per the partial-resolution rule). The dedicated design pass is done — the credential boundary is a host-side egress proxy that holds/injects/refreshes credentials so the live key never enters the sandbox; for MCP, the cleaner "supply credentials to the server at launch, tool calls carry no secrets" path is the chosen shape. The contract seam (EnvSpec credential-shape + a refresh-capable `CredentialSource`) is reserved now; the proxy builds later with netpolicy's `egress-proxy` strategy.
- **Description:** D63 established the credential model: the library does **zero ambient credential reads**; credentials arrive as an injected `Env` snapshot populated **at the edge**. The CLI edge already honors this — control-eval cleans its env and passes only the keys Claude Code needs via `--env`. The **MCP surface is also an edge**, but its tools (`sandbox_create`/`sandbox_run` — `name, workdir, prompt, agent, model`) expose **no credential input**. For a caller (control-eval now, a daemon later) to inject per call, the tools need an explicit `env`/`credentials` input **and** the MCP edge must enforce the same no-ambient-read discipline (never fall back to the MCP *server's* own host env). Such a param must be treated as a **secret** — redacted from any tool-call logging/tracing (local stdio transport doesn't cross a new trust boundary, but the key must not land in logs).
  **The wrinkle (load-bearing, the reason this is PARKED not just a TODO):** MCP servers are designed for **agents** to call, and an agent should not be handling raw credentials — so passing a real API key as a *tool-call argument* is architecturally suspect. A cleaner alternative: supply credentials to the **MCP server at launch** (env/config), so it performs all operations under those fixed credentials and tool calls carry no secrets. That wants a proper **secure-secrets-handling** design. The upcoming **API-key (metered JV key) + adversarial-agent** context raises the stakes: a real billable key inside an untrusted sandbox makes exfiltration-prevention (network-isolation allowlist) load-bearing, not theoretical.
- **Trigger:** when the concurrent MCP orchestration surface (trial-engine P3) is taken up, or when a secure-secrets model is designed — whichever first.
- **Pointer:** `internal/mcpsrv/tools.go`, `internal/cli/mcp/` (tool schemas — add the credential input + no-ambient discipline). Credential model: [D63] (`Env` snapshot, `SecretsStagingDir`); principal/credential-bundle [D58]/[D63]. Design context: [session-layer.md](session-layer.md).

### DF39 — `$HOME` credential files are the last implicit ambient-credential bleed into the sandbox

- **Discovered:** 2026-06-16 · **Workstream:** public-layering (session-layer / trial-engine design)
- **Severity:** LOW–MEDIUM (security — implicit host credentials enter the sandbox; matters most for untrusted agents on a real key)
- **Disposition:** **RESOLVED-IN-DESIGN by [D95](../decisions/working-notes.md) ([secure-secrets.md](secure-secrets.md))**; build phased (kept here until built). Under D95 the `$HOME` credential mount becomes **caller-controlled and filtered** (never implicit) — the caller fully controls what credential material enters, and where an agent authenticates via the proxy-injected path, no host credential file enters at all.
- **Rides:** a **breaking** release *when built* (it changes a default) — but the scope test is not what gates it: this is D95's phased build, not a flag flip, and until that path exists an opt-in mount removes the only auth the non-brokered agents have. Out of v0.9.0, 2026-07-17.
- **Description:** yoloAI bind-mounts the agent's host credential/state directory (e.g. `~/.claude`) into the sandbox so the in-container agent authenticates. After D63 removed ambient credential reads from the library proper — and with the CLI edge otherwise cleaning the env to only required keys — this `$HOME` mount is the **last implicit ambient-config source**. It contradicts the caller-injects-everything model, and in the adversarial-agent + real-JV-key world it means the user's **actual host credentials can be mounted into an untrusted sandbox** (leak/exfil vector + an unaccounted auth path that may not even be the intended billing principal). Eventual shape: the caller fully controls what credentials enter; the `$HOME` credential mount becomes **opt-in**, not implicit.
- **Trigger:** when API-key / adversarial usage becomes routine (the Anthropic JV engagement), or when DF38's MCP credential model is designed — whichever first.
- **Pointer:** the agent-state / credential bind-mount wiring (per-agent definition `state directory` → provision mount setup); contrast the env-var credential path under [D63]. Related: DF38.

### DF41 — the carve orphans the agent-free root work fused into `entrypoint.py` (each layer must claim its piece)

### DF50 — a headless agent with a present-but-invalid credential can still hang; the durable fix is a headless launch with no answerable TTY

- **Discovered:** 2026-06-26 · **Workstream:** Phase 1a (D101, headless-auth fallback)
- **Severity:** LOW
- **Disposition:** PARKED
- **Description:** D101 gates headless on *observed* auth (`agentHasUsableAuth`), which covers the
  common no-auth case (→ TTY fallback). But "credential present" ≠ "credential valid": an expired
  token still presents a file/env var, so an agent that re-authenticates on expiry (Gemini, Codex)
  could still launch a login/browser flow and **hang** in a headless pane. The auth-presence check
  can't detect validity. The durable, agent-agnostic fix is to run headless with **no answerable
  interactive TTY** (close stdin / no PTY the agent can block on), so any interactive login attempt
  fails fast instead of stalling — but today the headless flow runs the agent in the tmux pane (a
  PTY) to reuse pane-death detection (D100), so it *has* an answerable terminal. This ties to the
  session-carve's no-TTY headless mode. Until then the auth-presence gate + `run --tty` escape hatch
  are the mitigation.
- **Expired-precedence angle (broker, 2026-06-28).** The same "present ≠ valid" blindness governs
  credential *selection*, not just the headless hang. Auth gating keys on env-var/file **presence**
  via `HasAnyAPIKey`: when any of an agent's `APIKeyEnvVars` is set, the `AuthOnly` on-disk seed
  (Claude's `~/.claude/.credentials.json`) is suppressed (`shouldSkipSeedFile`), and the broker's
  `SelectCredential` picks the first *present* env credential. So env beats file unconditionally. The
  benign case (file expired, env valid) resolves correctly — the stale file is never seeded and the
  valid env credential is brokered. The footgun is the inverse: **env credential present but
  expired/invalid while the on-disk file is still valid** → the good file is suppressed and the dead
  env credential is brokered, so the agent 401s upstream despite a working credential existing on
  disk. Pre-existing (env-over-file precedence predates brokering; the broker just forwards the
  selected credential faithfully). A real fix needs validity awareness, not just presence — the same
  root cause as the headless-hang variant above.
- **Pointer:** `internal/orchestrator/create/create.go` (`agentHasUsableAuth`); the headless launch
  runs in the tmux pane via `runtime/monitor/sandbox-setup.py` (`launch_agent`). Expired-precedence:
  `internal/envsetup/envsetup.go` (`HasAnyAPIKey`, `shouldSkipSeedFile`), `internal/agent/agent.go`
  (`BrokerConfig.SelectCredential`). Related: D100, D101, D105, session-layer.md.

### DF104 — `--network-isolated` is IPv4-only: nothing in the repo configures `ip6tables`, on any backend

- **Discovered:** 2026-07-15 · **Workstream:** AC10 — running the apple backend's `--network-isolated` path end-to-end for the first time, which is exactly what "not just the raw-iptables capability" was meant to surface
- **Severity:** MEDIUM (a security property with an unfiltered protocol; **latent, not currently exploitable** — see below. It would become live the moment any backend's guest gets a globally-routable IPv6 address, with no code change and nothing to notice.)
- **Disposition:** PARKED — filed, not fixed. Adding an `ip6tables` default-deny touches the shared firewall for every backend and needs its own verification per backend; AC10's scope was apple's end-to-end run, which passed.
- **Rides:** **any** release. Deferred out of v0.9.0, 2026-07-17: the fix is not release-gated, its verification needs a v6-routable network per backend, and the claim was corrected in the meantime. See [ipv6-network-isolation.md](plans/ipv6-network-isolation.md).
- **Description:** `runtime/docker/resources/firewall.py` builds the default-deny + allowlist as **IPv4 `iptables`/`ipset` rules only**. `grep -rn ip6tables` across the whole repo — Go, Python, shell — returns **nothing**, so no backend has ever filtered IPv6. Verified live in an apple sandbox created with `--network-isolated`: the IPv4 `OUTPUT` chain is correct and complete (gateway:53 accepted, `allowed-domains` ipset matched, everything else REJECTed), while `ip6tables -L OUTPUT` is **empty with policy ACCEPT**. The guest is not v6-less: it holds a global-scope address (`fd96:…/64`) and a v6 default route via the vmnet gateway.
- **Why it is not exploitable today, which is the whole of the mitigation:** the address vmnet hands out is a **ULA** (`fd00::/8`, unique-local, not internet-routable), so there is no v6 egress to allow or block — a `curl -6` to a non-allowlisted host fails with exit 7 like everything else. Nothing in the design guarantees that stays true. It rests on Apple's vmnet choosing not to hand out a GUA, which is not a contract we hold, is not asserted anywhere, and no test would notice it changing.
- **Two ways it turns live:** (1) any backend whose network gives the guest a routable v6 — Docker with `--ipv6` enabled, a future vmnet, an IPv6-capable CNI on containerd — silently loses the allowlist entirely for v6 traffic, because the rules simply don't exist there; (2) an allowlisted domain that resolves v6-only would still be reached, but **unfiltered** — the allowlist would not be what let it through.
- **The honest framing:** the capability is declared `NetworkIsolation: true` on every backend that sets it. That claim is IPv4-scoped and says so nowhere. Either the rules should cover v6, or the guests should have v6 disabled (`net.ipv6.conf.all.disable_ipv6=1` in the entrypoint) so the claim is true by construction.
- **Correction, 2026-07-17 (owner's call): the recommendation above is wrong — take the first route, not the second.** The original preferred disabling v6 as "cheaper, and matching how the isolation already prefers *impossible* over *filtered*". **That parallel does not hold.** Preferring "impossible" is right for a protocol nothing ever promised to route; it is not right here, because **the allowlist is a promise about destinations, and the destination does not choose its family.** `resolve_domains` asks for `AF_INET` only (`firewall.py:73`), so a domain the user *explicitly allowlisted* that resolves AAAA is, under a v6 disable, **unreachable** — and under a v6 default-deny with no v6 allowlist, **blocked**. Either way the allowlist silently fails to *allow*, surfacing as a network fault rather than a policy decision. Both shortcuts are therefore not cheap-but-adequate; they are **wrong**, and they regress legitimate use. Proper family-aware support is the only route that keeps the promise, and the only thing it takes away is v6 egress to *non*-allowlisted hosts — which is the hole, not a feature. Sized and planned in [ipv6-network-isolation.md](plans/ipv6-network-isolation.md); DF134 is the same family-blindness biting one step earlier.
- **Update, 2026-08-09 — measured on both platforms, and the v6 half is not the v4 half with a different constant.** macOS (`design/research/macos-isolation-spike/results/pf-v6-hole.txt`): the hole is **universal, not apple-only** — both apple and tart guests hold a ULA *and* a link-local, and with enforcement loaded and the v4 allowlist empty, v4 was refused while **v6 reached the same host on the same port** on both backends. pf can enforce v6 in the same anchor, so it is an omission. Linux (`design/research/linux-enforcement/results/l5b-ipv6-hole.txt`, `l5c`): latent here — no v6 route on the test host and docker ships v6 off — but the rule semantics that make it a hole are confirmed, an `ip saddr` rule in an `inet` chain counted 6 IPv4 packets and **0** IPv6 ones while an `ip6 saddr` rule counted the 6. Every allowlist rule the design writes is `ip saddr`-shaped. **The new constraint for [ipv6-network-isolation.md](plans/ipv6-network-isolation.md):** on macOS the table must hold **every** v6 address the guest holds, because source selection is per destination scope (a guest talking to a link-local host sources from its link-local, not the ULA the backend reports) and a guest can acquire more at any time via SLAAC or privacy addressing. A v4 table never has that problem, so "add a second table pair" understates the work. Both hosts lack v6 upstream, so a host that has one has a **wider** hole, not a narrower one.
- **Pointer:** `runtime/docker/resources/firewall.py` (`install_rules`, IPv4-only); `runtime/apple/apple.go:61` (`NetworkIsolation: true`); verified against a live apple sandbox 2026-07-15.

### DF129 — the provenance hook counts naming a path as reading it, so a long session launders its own citations

- **Discovered:** 2026-07-17 · **Workstream:** measuring the noise of D122's hook before extending it to source paths — the measurement demonstrated the defect on itself
- **Severity:** LOW–MEDIUM. It weakens a gate rather than breaking anything, but it weakens it **exactly where it is needed most**: the longer the session, the more paths have been named for reasons that are not reading, so the check decays as context grows and the agent's memory of what it actually opened gets least reliable.
- **Disposition:** FILED, not fixed — and the fix is not obvious, which is why it is filed rather than patched. `READ_TOOLS` includes `Bash`, and the check is a substring test over tool inputs, so any command that merely *mentions* a path clears every citation of it. That is the deliberate over-match bias (D122: *"Over-matching here is the safe direction — it yields a false pass, where under-matching yields a false accusation, and an accusation is what gets a hook disabled"*). The bias is right; what was not anticipated is how routinely a session names a file without opening it.
- **Description:** the ways a path enters a Bash input without being read are ordinary, not exotic:
  - a **commit-message heredoc** — commit bodies name the files they change, constantly;
  - a path as a **string literal in a test** being written (`_SRC = "runtime/tart/prune.go"`);
  - a **grep for the filename itself**, i.e. asking "did I touch this?";
  - an **`echo`** in a diagnostic.
- **Verified by execution, on the hook itself (2026-07-17).** Replaying the checker over a real session's transcript against the four finding commits it produced reported **zero** blocks. Truncating each replay to the transcript as it stood *when the finding was written* reported **two**, both true positives (`lifecycle/restart.go:197`, `seatbelt.go:168,172` — line numbers taken from grep output for files never opened). The difference was entirely self-inflicted: the commands run to investigate the fire (`echo "=== the fire: where did I cite seatbelt.go..."`, a script listing `"seatbelt.go"`, a grep for `seatbelt\.go` in the transcript) put the basename in the blob. **Asking whether you read a file marks it read.**
- **Why this is not just "tighten the regex".** Telling a read from a mention means parsing shell, which is the under-match direction the hook refuses on purpose. Options worth weighing, none free: restrict `Bash` matching to the argument position of known readers (`sed`/`cat`/`less`/`head`/`tail`/`rg`); drop `Bash` from `READ_TOOLS` and rely on `Read`/`Grep`/`Glob` (under-matches every `sed -n` in this repo's idiom); or key the check on tool *results* being non-empty for that path, which contradicts the hook's founding asymmetry.
- **The sibling.** `READ_TOOLS` also contains `Task`/`Agent`, so naming a path in a **subagent prompt** counts as the parent having read it. That is the same shape and arguably worse: the parent gets a *summary*, which is the precise thing the hook exists to distinguish (*"a summary in context and a source you read are indistinguishable from the inside"*). Delegation is most of how the work is done, so this is not a corner.
- **Pointer:** `scripts/check_citation_provenance.py` (`READ_TOOLS`, `read_tool_inputs`, and the substring test in `unread_citations`); `scripts/tests/test_citation_provenance.py` (`test_grep_and_bash_count_as_going_to_look` pins the behaviour, correctly, as intended); D122; [`research/llm-shaped-repos.md`](research/llm-shaped-repos.md) Part 7 "No provenance on a fact".

  panic cannot fire; the incompatibility itself remains.
- **Description:** `RunInterfaceConformance` calls `t.Parallel()` on every subtest of a non-sharing
  backend, and calls `setup(t)` *inside* those parallel subtests. A fixture whose setup uses
  `testutil.IsolatedHome` (which calls `t.Setenv`) then panics: Go forbids `t.Setenv` in a parallel
  test (`testing: test using t.Setenv ... can not use t.Parallel`). `appleSetup` is such a fixture,
  so apple with `SharesReadOnlyInstance: false` panics the whole suite — verified on hardware
  2026-07-19 (the Linux phase verified only docker/podman/containerd fixtures, none of which call
  `IsolatedHome` per-subtest; tart's closure captures its runtime once at parent scope). Any future
  fixture that isolates env per-subtest will hit the same wall the moment it opts out of sharing.
- **Remedy sketch:** either make the harness detect the combination and fail with a named error
  (cheap), or make per-subtest fixtures isolate HOME without `t.Setenv` (a Layout-only isolation,
  since the env leak the helper guards against is process-global anyway).
- **Pointer:** `runtime/runtimetest/conformance_iface.go` (`parallelize`, the non-sharing branch);
  `runtime/apple/integration_test.go` (`appleSetup`); `internal/testutil/home.go:33`.

### DF160 — `dind/podman-priv` times out on macOS, and the smoke harness turns a slow teardown into a crash

- **Discovered:** 2026-07-30, macOS release matrix (`make releasetest`) · **Workstream:** smoke reliability
- **Severity:** MEDIUM for the harness half — it destroys the run's own reporting, which is worse than the failure it is reporting. LOW–MEDIUM for the timeout itself, one occurrence on the heaviest cell in the matrix.
- **Rides:** any.
- **Two defects, and the harness one is the more valuable.**
- **(a) The test timed out.** `dind/podman-priv` — docker-in-docker inside a privileged podman container on macOS, i.e. a container in a VM in a VM — failed with *"harness timeout (sentinel not seen / command timed out)"*. Every other podman cell (`stop_start`, `tag_transfer`, `isolation_check`) passed, as did the whole seatbelt/tart/apple set. **Fixed: no.**
- **(a2) It reproduced on Linux, three times in one run, which retires the "needs a Mac" scoping (2026-07-30).** This entry said *"not reproducible from Linux; needs a Mac to diagnose"*. A Linux `releasetest` at `b5bc04cc` failed `stop_start/containerd-vm`, `stop_start/containerd-vmenhanced` and `tag_transfer/containerd-vmenhanced` on first attempt — same fingerprint, *harness timeout (sentinel not seen / command timed out)* — all three passing on the configured retry. So the defect is not macOS-specific and not podman-nesting-specific: it is **the heaviest virtualised cells against a fixed sentinel budget**, and the platform was a property of which cell happened to be heaviest, not of the bug.
- **(a3) What the autopsies show, which narrows it usefully.** The sandboxes were healthy: `sandbox.ready` at 16–26s on all three, no crash, `nothing fatal found in artifacts — the guest stalled rather than crashed`, host disk fine (73% used, 25G free). Then a ~110s gap with no events, then `sandbox.info` polling for ~178s until the 300s budget expired at ~310s elapsed. The baseline diff names the wall precisely: the last-good run reached `hook.active`, `sandbox.restart`, `sandbox.stop`, `sandbox.start`, `sandbox.apply` and 8 more; this run reached none of them. **The boot was never the problem** — everything up to and including a ready sandbox completed in under 30 seconds of a 300 second budget.
- **(a4) A plausible root cause that is cheap to check first, and a naming defect that hides it.** `QEMU_TIMEOUT = 300` is commented *"QEMU-based Kata VM — slower boot than Firecracker"*, i.e. it reads as a **boot** budget. But `SENTINEL` is *"touched in the exchange dir when the agent finishes its prompt"*, so the budget actually gates boot **plus** startup **plus** the agent completing a whole task. Those are different quantities with different variances, and the constant is named and documented for the smaller one. Note also the load asymmetry: VM cells are capped by a semaphore (`vm_cap`), container cells run through `_NULL_GATE` with no cap, so a VM cell can be sharing the box with every container tier at once. Before raising any number, establish whether the agent was working or wedged during that 110s gap — the stall detector did **not** fire (`stall_grace_secs=120`, so it was armed), which suggests the sandbox kept reporting a non-idle status throughout.
- **(a5) Recurred 2026-08-01 (macOS, `036343c3`), and this time the RETRY failed too — on a much lighter command.** Attempt 1 timed out at 120s inside the dind `exec` (start `dockerd`, then `docker run hello-world`); the sandbox itself was healthy again (`sandbox.ready` at 3s, agent active at 6s, and the autopsy's baseline comparison records that it *reached every step the last-good run did*). The destroy that followed then exceeded 30s (`TIMEOUT destroy … left for end-of-run cleanup`), and the retry failed at **`yoloai new … --no-start`, timing out after 60s** — a create that does not even start a container. A fresh 60s create does not time out on an idle Mac, so the most economical reading is a **cascade**: the wedged privileged podman container from attempt 1 outlived its destroy and loaded the host through the retry. That is evidence *against* the pure "the sentinel budget is too small for the heaviest cell" reading in (a4) — the retry's budget was never the binding constraint — and *for* teardown of a wedged nested-virt cell being the thing that actually needs fixing. Check whether the leaked container is still running when the retry starts before touching any timeout constant.
- **(a6) Baseline measured 2026-08-04 on an idle Mac: the cell takes 6.5 s against a 120 s budget, so this is a stall, not a tight budget.** Run in isolation (`smoke_test.py --test dind --backend podman-priv`) on a quiet host — load average ~3.5, no other cells, podman machine idle — `dind/podman-priv` passed with `elapsed_s: 6.5`. The 52 s wall-clock of that invocation was almost entirely the five prerequisite base-image builds, not the cell. **That is ~18× headroom**, which is strong evidence against the "the sentinel budget is too small for the heaviest cell" reading in (a4): a cell that finishes in 6.5 s does not creep to 120 s under load, it *stops*. Raising the constant would buy nothing and would lengthen the failure.
- **(a7) (a4)'s sentinel reasoning does not apply to this cell, and the real budget is a different one.** (a4) argues that `QEMU_TIMEOUT` is documented as a boot budget while `SENTINEL` actually gates boot + startup + the agent completing a task. True in general, but the dind cell creates its sandbox with **`--agent idle`** — no model inference, no sentinel — and its failing step is an `exec` with a **hardcoded `timeout=120`** (`scripts/smoke_test.py:2678`), unrelated to `QEMU_TIMEOUT`. So the timeout that fires here is not the one (a4) analyses, and tuning sentinel budgets cannot affect it.
- **(a8) The exec contains an external network dependency, which is the untested stall candidate.** Its script is: background `sudo dockerd`, poll `docker info` for **at most 30 iterations**, then `sudo docker run --rm hello-world`. The readiness wait is therefore bounded at ~30 s and fails *fast* rather than timing out — so a 120 s expiry has to land in `docker run`. And that step pulls from Docker Hub on every run: the inner daemon's image store is empty each time, and this run's log shows `Unable to find image 'hello-world:latest' locally` / `Pulling from library/hello-world`. **A hypothesis, not a finding:** an anonymous Docker Hub pull inside a nested daemon is rate-limited per source IP and can stall for reasons that have nothing to do with host load or a wedged container — which would explain a 120 s expiry on an otherwise 6.5 s cell, and would explain it recurring on the *heaviest* runs only because those issue the most pulls. **Next recurrence: capture whether the pull had started and whether Docker Hub returned a rate-limit response**, before attributing it to load. Pre-pulling `hello-world` into the inner daemon, or vendoring it, would remove the dependency from the budget entirely.
- **(b2) The (b) fix is confirmed working in production, which had not been observed before.** This run hit exactly the path that crashed the matrix on 2026-07-30 — a destroy exceeding its timeout on the retry path — and the run survived it: every other cell reported, `summary.txt` and `rollup.txt` were both written, and the end-of-run sweep reclaimed the survivor (`post-run sweep: clean`). Recorded because DF88 is the standing lesson that a fix believed correct and never observed firing is not the same as a fix known to work.
- **Not caused by the tiering branch.** The run was `036343c3` (the sandbox-share-tiering tip at the time). Every backend the branch touches passed — `stop_start` on seatbelt, tart and apple, `tag_transfer` on seatbelt — and nothing in that commit is reachable from `new`/`exec`, since migrators run only under `system migrate`. 18 of 19 cells passed.
- **Not the guest-readiness race, and the check is one field.** [DF28](#df28--kata-guest-readiness-race-under-back-to-back-vm-churn-task-not-found--exec-enoent) was briefly cross-linked here as this entry's earlier sibling and as the mechanism it "stops short of". That was wrong, retracted 2026-08-02. DF28's failures occur *before* `sandbox.ready` — a probe that cannot exec into a not-yet-addressable task — and every cell here reached `sandbox.ready` in 16–26s and stalled afterwards. **`sandbox.ready` is the discriminator**, and this entry's own (a3) already said "the boot was never the problem". The two share a symptom profile (heaviest virtualised cells, churn, green on retry) and nothing else established.
- **The family it more plausibly belongs to is the agent-side one.** A stall that begins after readiness, consumes no tokens and never reaches `hook.active` is [DF13](#df13--a-swallowed-submit-key-parks-the-agent-on-a-prompt-it-never-runs-the-trust-dialog-is-one-cause-not-the-cause)'s shape — an agent parked on a prompt it never ran. That is a hypothesis, not a finding: DF13's 2026-07-17 mitigation logs `prompt.submit_retry` / `prompt.submit_unconfirmed` precisely so a real occurrence announces itself, so **the next recurrence should be grepped for those two events before any other theory is entertained**. The 2026-08-01 macOS artifacts do not settle it — that run's only failure was the dind `exec`, which had reached `prompt.deliver` and is a different thing again.
- **Not DF159.** No `ttrpc: closed` in any of the three; that finding remains a separate, single-occurrence containerd flake. Worth noting the harness has a fingerprint table that auto-labels known flakes (DF8, DF86 are in it) and **DF159 is not**, so a recurrence of *that* would not self-identify either.
- **(b) The cleanup then crashed the run, and that IS fixed.** The retry path called `_destroy_named_sandboxes`, `yoloai destroy --abandon-unapplied` exceeded its 30s timeout, and the `subprocess.TimeoutExpired` propagated out of the worker thread through `future.result()` and killed the whole matrix with a Python traceback. Five further podman destroys then timed out at >60s during end-of-run cleanup. So a slow teardown on one backend discarded the summary and JUnit record of every test that had already passed.
  The sibling path had been hardened and this one had not: the end-of-run cleanup already catches `TimeoutExpired`, prints `TIMEOUT destroy …`, and falls back to `yoloai system prune`. Two loops calling the same command, one defended. Now `_destroy_named_sandboxes` catches it too — **and leaves the survivor on `ctx.sandboxes`**, so the end-of-run sweep and the prune fallback get another attempt; dropping a name whose sandbox still exists is how a leak outlives the run.
- **(c) The reporting consequence, which is why this was hard to see.** A crashed provider cycle writes no `summary.txt`; a passing one does. `--all-docker-providers` gave each provider its own top-level timestamped directory, so the failing run left a sparse directory with no summary while the *passing* run left a complete one — and the complete, convincing artefact was the one uploaded for diagnosis. Compounding it, only the **first** provider runs the full matrix and later ones cover docker tiers alone, so the passing directory legitimately contained only `docker`/`docker-priv` results. Read alone it looks exactly like a coverage hole, and was briefly mis-diagnosed as one here.
  Fixed: every provider now lands in one umbrella directory (`…-all-providers/<provider>/`) with a `rollup.txt` recording each provider's PASS/FAIL, its scope, and the fact that a docker-only subdirectory is by design. One directory to upload, and it explains itself.
- **What to capture if (a) recurs:** whether the inner dockerd ever started, the podman machine's own load at the time, and whether `destroy` was slow because the sandbox was wedged or because podman-macOS teardown is simply slow under that nesting. The five unrelated destroys timing out at >60s in the same run points at the latter.
- **Pointer:** `scripts/smoke_test.py` (`_destroy_named_sandboxes`, `_provider_child_argv`, `run_all_providers`); `scripts/tests/test_smoke_cleanup_resilience.py`. Sibling: [DF159](#df159--exec-start-ttrpc-closed-on-containerd-vmenhanced-during-apply-once-in-38-runs) — both are smoke-reliability findings where the diagnostic surface, not the defect, was the expensive part.

### DF163 — containerd's `log.txt` has no writer and is in no mount, so `Logs()` always returns empty

- **Discovered:** 2026-07-30, reviewing the sandbox-tiering plan's late file classifications against the code · **Workstream:** sandbox-dir tiering / containerd
- **Severity:** LOW as a defect (a diagnostic returns nothing where it looks like it returns something), MEDIUM as a documentation problem — three comments describe a mechanism that does not exist, and one of them is the constant's own doc.
- **Rides:** any.
- **What is wrong.** `config.ContainerLogPath` (`<sandboxDir>/log.txt`) has exactly one consumer in the tree: `runtime/containerd/logs.go:23`, a **read**. There is no writer — none in Go, none in the guest Python — and the path appears in **no `MountSpec`**, so no guest can write it either; containerd's own task is created with null IO. `Runtime.Logs()` therefore reads a file nothing creates and returns `""` on every call, which its "returns empty string if the log file does not exist" contract makes indistinguishable from an empty log.

Which one depends on whether a log tail is wanted for containerd at all; `logs.go:48` already suggests `cat <sandbox>/log.txt` to users as a diagnostic, so today that advice points at a file that never exists.

Filed under rule 7 rather than fixed in scope, because the fix is a decision about containerd's diagnostics.
- **Pointer:** `runtime/containerd/logs.go`, `runtime/containerd/lifecycle.go:467`, `internal/config/sandbox_layout.go:78-80,237-239`.

### DF164 — the pre-v6 migrators address the sandbox layout through the live path builders, so tiering silently breaks them and their tests hide it

- **Discovered:** 2026-07-31, attempting step 3c of the sandbox tiering (moving `ro/` and `rw/`) · **Workstream:** sandbox-dir tiering
- **Severity:** HIGH for anyone upgrading. A pre-v6 sandbox becomes unmigratable, and the failure is silent: the migrators do not error, they look in the tiered location, find nothing, and report "nothing to migrate".
- **Rides:** must land with the v5→v6 `TierLayout` migration; it is the same change.
- **The defect.** Every migrator below v6 reads a sandbox written **flat**, but they address it through the live builders — `store.EnvironmentFilePath`, `store.WorkDir`, `store.OverlayLowerDir`. Those builders now resolve into `host/` and (once 3c lands) `rw/`. So each migrator asks where a file is *in the layout it is migrating to*, looks there, and finds nothing. `migrateAgentConfigRecord` returns `nil` on `fs.ErrNotExist` — "a partial/dormant directory with no record to migrate" — which is exactly the wrong answer for a sandbox that has a record, flat, one directory up.
- **Already live, not hypothetical.** The `host/` move landed in the branch's step 2, so `migrate_agentcfg.go` and `migrate_principal.go` were pointing at `host/environment.json` the moment it did. **All three migrators are now era-pinned**, and the durable rule has graduated to [standards/go.md § A migrator addresses the layout of its own era](../standards/go.md) — cite it there, not here. The finding stays open until the v5→v6 `TierLayout` migrator itself lands, which is the same change.
- **One clause of this entry was wrong, and the correction is the useful part.** It called `migrate_overlay.go`'s `if e.Name() == "work"` scan a defect "a tiered root no longer satisfies". It is not: that walk enumerates a *flat* v3 sandbox's root, where `work/` is exactly what sits there, so the literal was already era-correct — the only hazard was that nothing said so, leaving it one tidy-up away from becoming `config.WorkBasePath`. It now reads `pretier.WorkDirName` and says why. The general point: "addresses the layout of its own era" is the rule, and a *literal* satisfies it. Grepping for live-builder calls finds the violations; grepping for literals finds the compliance.
- **Four of the pinned sites are not yet provable, and step 3c is what makes them so.** In `migrate_overlay.go` the `work/` paths — the two source resolvers, the capture stage, and the rebuilt destination — read identically whether spelled `pretier.WorkDirFor` or `store.WorkDir`, because `work/` is deliberately still flat while `ro/`+`rw/` wait. Reverting any of those four leaves every test green: this is rule 10's coincidence trap, where two values agree today and the change is invisible to any check. The flat-literal fixtures in `migrate_overlay_test.go` become their red-on-revert the moment 3c moves `work/` into `rw/`. **Re-run the four reverts as part of 3c** — that is the step where they start meaning something, and where an unpinned one would otherwise ship silently.
- **`store.OverlayLowerDir` is retired,** on the owner's call: its documented purpose ("the one overlay path the v3->v4 flatten migrator still reads") moved to `pretier.OverlayLowerFor`, since a pre-v4 *and* pre-tier path is frozen twice over, which left it a second mechanism for a job that now has one owner (rule 7's converse). Removed with a BREAKING-CHANGES entry (Go embedding surface); the release was already breaking, so the version field did not move.
- **The part worth recording: the tests were updated to follow the move, so they certify the break.** Commit `f3bd546b` changed `migrate_agentcfg_test.go` from `filepath.Join(sandboxDir, store.EnvironmentFile)` to `store.EnvironmentFilePath(sandboxDir)` — i.e. it re-seeded the fixture at the *new* location. The test then passes because the fixture and the migrator agree with each other, while neither agrees with any sandbox that exists on disk. **A migrator test that builds its fixture with the same builder the migrator reads with cannot fail**, whatever the layout does. This is the exact hazard that made the backend tests keep literal paths in `ff7f7499`; migration fixtures need the same treatment for a stronger reason, because their whole subject is a layout that is no longer current.
- **Why it blocks 3c rather than being fixable inside it.** Making the migrators era-correct means deciding *how* migrators address the layout, and there are two coherent answers with different blast radii: (a) **era-pinned paths** — a frozen pre-tier path module each migrator uses, so every migration reads and writes the layout of its own version (tried; it works for reads, and for writes it needs `SaveAt`-style variants of `SaveEnvironment`/`agentcfg.Save`/`netpolicycfg.Save`, because a migrator that reads flat and writes tiered leaves the flat record stale and re-migrates forever); or (b) **run the tier move first**, as a pre-pass ahead of the numbered ladder, so every other migrator can keep using the live builders unchanged. (b) is materially simpler and makes the pre-tier module unnecessary; it costs making one migration step version-independent, which is a real departure from how the ladder works. **This is the plan's "migration shape" open question, arrived at from the other end.**
- **Interim state on the branch:** `work/` is deliberately left flat while the rest of `rw/` waits, because `work/` is the one tier member a pre-v6 migrator walks. `host/` has already moved and the migrators reading it are already wrong — that is inside the branch's known "an existing sandbox reads as missing" window, but it is a *different* defect from the missing `TierLayout` migrator and would survive it if not fixed.
- **Design settled 2026-07-31: [migration-by-duplication.md](../archive/plans/migration-by-duplication.md)**, and the answer to *this* finding is the smaller half of it. The mechanism duplicates the sandboxes tree into scratch, verifies it there, and promotes once — but that is about a failed migration leaving a tree the *old* binary still reads, and it does nothing for DF164. The fix here is **era-pinning**, chosen over the pre-pass this entry called "materially simpler": a pre-pass has to recognize an already-tiered sandbox by sniffing its shape, against the plain-int-stamp rule (D61). So every pre-v6 migrator gets literal flat paths for reads and writes, `SchemaTiered = 6` runs last, and the durable output is the rule — *a migrator never addresses through the live path builders* — not the pin. An earlier draft of that plan carried a resumable staged ladder; it was retracted (see its § What the constraints deleted).
- **Pointer:** `internal/orchestrator/migrate_agentcfg.go`, `migrate_principal.go`, `migrate_overlay.go` (incl. the `"work"` literal at :236); their tests; [sandbox-share-tiering.md](../archive/plans/sandbox-share-tiering.md) step 4.

- **Severity:** MEDIUM. Not a data-loss defect; a truthfulness defect in a safety claim, which is worse than it sounds because the claim is what someone will rely on when deciding whether an upgrade is safe to attempt.
- **Rides:** any.
- **What is wrong.** The migration framework's guarantee is that a failure before the promoting rename leaves the live directory untouched, so the previous binary keeps working. `PrincipalRename` breaks the second half: it renames real containers and VMs (`runtime.Renamer.Rename`, `internal/orchestrator/migrate_principal.go:183`) and removes instances that cannot be renamed (`:203`). Those are not stageable and not discardable. A failure in a *later* migrator therefore leaves an untouched v4-shaped directory naming `yoloai-<name>` beside instances already called `yoloai-cli-<name>`, and the old binary finds its sandboxes missing.
- **Survivable, and that is not the point.** A re-run tolerates the absent old name (`errors.Is(err, runtime.ErrNotFound)` at `:183`) and re-derives the new one, so the state converges forward. The defect is that "any failure leaves the live dir untouched" is stated without the caveat, in a subsystem whose whole purpose is to be trustworthy about exactly this.
- **The general shape, which is the part worth keeping.** *Any migrator step with an external side effect is outside the transaction.* Instance renames are today's instance; host artifacts (CNI netns, tmux process groups, injector processes — see D114) are the obvious next ones. A design that wants a real all-or-nothing guarantee has to either forbid external effects in migrators, or split each migrator into a stageable on-disk half and a re-runnable reconciliation half that runs *after* the promotion.
- **Not fixed here.** `PrincipalRename` shipped in v0.9.0 and is crash-tested; restructuring it is not in the tiering workstream's scope, and the v5→v6 tier move has no external effects of its own. Filed under rule 7.
- **Pointer:** `internal/orchestrator/migrate_principal.go:178-207`, `internal/migrate/driver.go:31-37`, [migration-by-duplication.md](../archive/plans/migration-by-duplication.md) § What this does not cover.

- **Discovered:** 2026-08-02, asking why `SupportsAgentFreeLaunch` excludes container-enhanced · **Workstream:** launch / isolation
- **Severity:** MEDIUM, and the consequence is a *missing capability*, not a weak one. **Corrected 2026-08-02** — this bullet first said gVisor "silently gets the weaker in-container iptables the agent could tamper with". Measured on this host: rules installed in the **container's own netns** — which is what the shipped sidecar does — are **bypassed entirely** by gVisor (`OUTPUT` and `FORWARD` DROPs present, egress still succeeded), because the Sentry injects frames at L2 below netfilter's IP hooks. Rules in the **host root netns** keyed on the sandbox IP (`DOCKER-USER`) **did** block it. The launched process would run as the stale image UID, its first write would `EACCES`, and the detached launch swallows the error. All true.
- **But the remedy already existed, three months earlier.** `store.ContainerUser` returns the **numeric host UID** under container-enhanced for exactly this reason — a numeric uid has no name to resolve — and its docstring describes the same defect in the same words. The launch path never adopted it: `launch.go` still hardcodes `User: "yoloai"`, and the whole isolation mode was excluded instead. This is rule 7's converse — *a sibling path already solves it* — and the second mechanism here is the exclusion itself.
- **Verified by experiment, not by reading (2026-08-02).** A throwaway binary with two changes — `SupportsAgentFreeLaunch` returning true, and the launch user made numeric under container-enhanced — brought up a real `--isolation container-enhanced` sandbox on this host's `runsc`. It took the agent-free path (`entrypoint.keepalive_only`, "no agent launched"), wrote `.substrate-ready`, launched the session-runner, and the agent ran: `session-runner.log` owned by the **host** user rather than the stale image UID, `sandbox-setup.py` running as `yoloai` against the live passwd, `agent-status.json` active, and an agent write reaching `yoloai diff`. The failure mode the exclusion describes did not occur.
- **What a real fix has to do beyond the experiment.** Route the launch user through the *same* decision `store.ContainerUser` makes rather than adding a third spelling of it — the experiment's inline helper is a fourth. Note `ContainerUser` also handles `UsernsMode == "keep-id"` (returns empty, for rootless podman), which the launch path does not consider today and which matters the moment a keep-id backend opts into agent-free. And removing the exclusion changes which sandboxes get the sidecar firewall, so it needs the `runtimetest` isolation coverage run on gVisor, not just a green create.
- **Pointer:** `runtime/isolation.go` (`SupportsAgentFreeLaunch`), `internal/orchestrator/launch/launch.go:436` (`User: "yoloai"`), `store/environment.go` (`ContainerUser`), `internal/orchestrator/launch/launch.go` (`UsesSidecarFirewall`).

### DF172 — the vmnet subnet re-pick strands apple sandboxes too, and apple has no net-health detector

- **Discovered:** 2026-08-02, measuring host `pf` enforcement for the two macOS VM backends · **Workstream:** isolation / macOS
- **Severity:** MEDIUM
- **Disposition:** RESOLVED 2026-08-03 for the detector half; the test-design rule below stands
- **Rides:** **any.** Detection is additive; it withdraws no promise.
- **Description:** A macOS VM sandbox can be `running`, hold its assigned IP, and have zero egress — the known vmnet subnet re-pick leaves VMs stranded on a dead epoch. tart detects this and reports `(net-dead)` via `runtime.SandboxNetHealthProber`; **apple has no equivalent probe**, so `yoloai ls` reports a healthy sandbox that cannot reach anything. Separately, a sandbox in this state makes any "egress is blocked" conformance assertion pass vacuously. (An earlier version of this entry also claimed the two macOS backends cannot hold vmnet bridges at the same time — retracted below; they coexist fine.)
- **This is mostly a rediscovery, and the known part is the load-bearing part.** The vmnet bridge churn itself is already catalogued: [backend-idiosyncrasies.md](../backend-idiosyncrasies.md) § *Tart: vmnet session wedges* records "subnet flapping under session churn" — tart's bridge "is torn down and re-created as tart VMs come and go, and macOS re-picks its subnet on re-creation (`192.168.64.x` ↔ `192.168.65.x` within minutes on the same host)" — and DF87 covers the stale-lease false-healthy variant. I observed exactly that re-pick and initially wrote it up as new. **Two things are genuinely new**, below; everything else here should be read as confirmation.
- **~~New (1): the epoch change crosses backends~~ — RETRACTED 2026-08-02, same day, by a controlled re-run.** This bullet claimed tart and apple "cannot both hold a vmnet bridge", that starting one "stranded" the other, and that it alternated "four times, deterministically, most-recent-start wins". **That is false.** Driving the switch deliberately (`vmnet_switch.sh` in [macos-isolation-spike](research/macos-isolation-spike/README.md)) produced **three coexisting bridges** — `bridge100` 192.168.139.3 (Docker Desktop), `bridge101` 192.168.64.1 (apple), `bridge102` 192.168.65.1 (tart) — with **both backends at working egress simultaneously at all four checkpoints**, including immediately after a `container system` restart with tart running, and after a tart VM restart with apple running.   **What I actually saw, and why it looked like exclusivity.** The original observations were all made on a host whose container-framework vmnet was *already* in the broken state this entry opens with (new VMs coming up `NO-CARRIER`), where only two bridges existed and index 101 was being recycled between backends with a different subnet each time. Under those conditions a bridge teardown/re-create does strand whatever was attached to the old epoch — which is precisely the **already-documented** "subnet flapping / cross-epoch survivor" behaviour, not a new cross-backend exclusivity. I generalised a repeated symptom into a mechanism, on a host that was misconfigured for the whole observation window, and attached a causal verb ("stranded", "most-recent-start wins") to n=4. Coexistence is the normal case.
  **What survives:** a bridge that is torn down and re-created can come back on a *different subnet*, and VMs still attached to the old one go silently net-dead — true, cross-backend as well as within tart, and already recorded. The `runtime/apple/reach.go:31-37` assumption ("persists while the `container` system service runs") is still worth re-checking against that, but the counter-example I offered for it does not hold.
- **New (2): the detector is tart-only, and DF86 is why that matters.** DF86 ("a wedged tart vmnet session poisons networking for all NEW VMs on the host", `findings-resolved.md`) is the closest prior art and it is the *same escalation one backend short* — it found the blast radius was the host rather than the one VM, and it was closed by shipping detection: `runtime.NetLivenessReporter` + `runtime.SandboxNetHealthProber` in `runtime/tart/netcheck.go`, surfacing `network: WEDGED` in `doctor` and `idle (net-dead)` in `ls`. That remedy was never extended past tart. `SandboxNetHealthProber` is still implemented by exactly one backend (`runtime/tart/netcheck.go:22`). Verified: with the apple sandbox holding a valid IP and zero egress, `yoloai ls` reported it plainly `active`, no marker. So the finding is not "we need a detector" — it is "**DF86's detector needs an apple implementation**", and DF86's is the template.
- **The test-design consequence, which is the sharper one.** [tamper-resistant-network-isolation.md](plans/tamper-resistant-network-isolation.md) proposes a conformance assertion of the form "egress to a non-allowlisted destination is refused" (its § Acceptance test). A sandbox in this state **passes that for free, on every destination**, because it has no network at all. This is [A22](../agent-failures.md) with a platform-level cause rather than a shell-quoting one, and it is not hypothetical: it silently invalidated the first run of the `pf` research harness. Any macOS network conformance case **must** assert a permitted destination still succeeds in the same run, or it certifies nothing. (The sibling plan, host-controlled-agent-launch.md, asserts agent-process presence rather than egress, so it is exposed to a different vacuity mode, not this one.)

Key on the sandbox address — see [tamper-resistant-network-isolation.md](plans/tamper-resistant-network-isolation.md) § The macOS half.
- **Not yet established.** Not the exclusivity question — that one is answered and retracted above. What remains open is narrower: whether **bridge re-creation** strands VMs of the *other* backend on a second Mac as it did here, and whether the subnet re-pick is deterministic or opportunistic. Cheap to check on another machine; neither answer changes the apple detection gap, which is the actionable half of this entry.
- **RESOLVED 2026-08-03 (the actionable half).** apple now implements `runtime.SandboxNetHealthProber` in `runtime/apple/netcheck.go`. It needs **no guest exec**: `container inspect` reports the container's own `ipv4Address` *and* the `ipv4Gateway` it was given, so the wedge reduces to a pure host-side question — is that gateway still assigned to an interface? That is exactly this finding's mechanism, since a re-created bridge leaves the container holding an address and gateway from the dead epoch. Verified end-to-end against an unpatched control: `ls --json` now carries `net_health="ok" detail="192.168.64.6"` for a healthy apple sandbox where it previously carried nothing.
  **What is NOT verified:** the WEDGED branch itself, on hardware. The vmnet subnet re-pick cannot be induced on demand, and the obvious proxy — stopping the container service — turns out to exercise a different state entirely (the sandbox reads `removed`, so the probe never runs). The classifier is unit-tested on all six branches with the real captured `container inspect` output pinning the parser, and the OK path is hardware-verified; the wedge verdict rests on the same host-interface comparison tart's has used since DF86.
  **A by-product worth more than the probe:** making the host state visible produced [DF178](#df178--apples-vmnet-bridge-is-created-by-the-first-container-not-by-the-system-service-so-the-injector-is-unbindable-on-a-fresh-host), which refutes the bridge-persistence assumption this entry had already flagged as worth re-checking.
- **Still open:** the vacuous-conformance consequence (a net-dead sandbox passes "egress is refused" for free) is a test-design rule, not code, and is unaffected by the detector landing.
- **Pointer:** `runtime/apple/netcheck.go` (the detector, now built), `runtime/tart/netcheck.go:22` (the template), `runtime/apple/reach.go:31-37` (bridge-persistence assumption — now DF178), `runtime/tart/reach.go:19-22` (per-VM bridge lifecycle), `runtime/apple/apple.go:68` (`NetworkIsolation: true`).

### DF173 — a documented root cause rests on a mechanism the code does not use: `patchKeepaliveOnly` is an in-place write, not an atomic rename

- **Discovered:** 2026-08-02, while measuring host→guest file coherence on tart · **Workstream:** launch / macOS
- **Severity:** LOW
- **Disposition:** RESOLVED 2026-08-03
- **Rides:** **any.**
- **Description:** Both the code comment at `internal/orchestrator/launch/launch.go:376` and the `backend-idiosyncrasies.md` entry "Docker Desktop: a single-file bind mount serves stale content after the host atomic-renames it" explain a real, reproduced failure by attributing it to a new inode: the code comment reads "The file patch is an atomic rename (new inode)" and the idiosyncrasy entry expands that to "(write temp + rename)", with Docker Desktop's gRPC-FUSE caching the path→inode mapping. But `patchKeepaliveOnly` calls `fileutil.WriteFile` → `os.WriteFile` (`internal/fileutil/fileutil.go:144-149`) — an in-place truncate+write that **keeps** the inode. The symptom was real and the shipped fix (the `YOLOAI_KEEPALIVE_ONLY` env var) works regardless, so nothing is broken today; what is wrong is the *explanation*, in two places, and it is wrong in the one dimension that matters if anyone reasons from it.
- **Why it is worth an entry rather than a silent edit.** The sibling writer of the same file, `patchRuntimeConfig` (`internal/orchestrator/lifecycle/runtimeconfig_patch.go:32`), *does* use `fileutil.AtomicWriteFile` (`:47`) — so the repo contains both idioms, on one file, and the docs attribute one writer's behaviour to the other. Deciding which is correct requires re-testing the Docker Desktop case; either the comment is stale (a writer changed) or the original diagnosis mis-identified the mechanism. Do not "fix" the prose by guessing.
- **Adjacent, and the reason it surfaced now.** tart's VirtioFS was measured 2026-08-02 to never propagate an **in-place** host overwrite to the guest (see the new idiosyncrasy entry); rename-replacement was not tested there. So "which writer does this path use" becomes load-bearing for tart as well as Docker Desktop the moment any guest reads a host-rewritten file *while running*. **Today none does, and the check bounded the concern rather than confirming it:** `yoloai network allow` rewrites `runtime-config.json` on a running sandbox via `Engine.SaveNetworkAllowlist` (`internal/orchestrator/engine_network.go:23`) → `PatchConfigAllowedDomains` → `patchRuntimeConfig`, but that file is consumed by the guest at **next start**, not polled — the live in-container update is a separate exec path (`LivePatchNetwork`, `:37`, whose own comment states "the on-disk allowlist is the source of truth and the change is queued for the next start"). A fresh boot has no stale cache, so the current design is safe by accident of consumption timing, not by choice of writer.
- **RESOLVED 2026-08-03 — and it did not need the re-test this entry demanded.** The entry said deciding between "the comment is stale (a writer changed)" and "the original diagnosis mis-identified the mechanism" required re-running the Docker Desktop case. It did not: `git log -L` over the function shows `patchKeepaliveOnly` was **introduced** with `fileutil.WriteFile` (`722b62ee`) and has never used anything else. So there was no writer change, every reproduction of the symptom ran against an in-place write, and the rename premise never described this code. That is the second option, settled from history for the cost of one command.
  **What was corrected, and what deliberately was not.** Both the code comment and the idiosyncrasy entry now describe the observation — a host rewrite of a single-file bind mount is not visible in the container promptly — and drop the inode story. The cache-internals explanation ("gRPC-FUSE caches the path→inode mapping") was *inferred from* the false premise, so it is now stated as **not established** rather than replaced with a better guess. Correcting a wrong mechanism by inventing a different one would have reproduced the defect this finding is about.
  The general rule in `backend-idiosyncrasies.md` was already written in terms of the observation rather than the mechanism, which is why it survived the premise being wrong — that is the transferable lesson, and it is now said in the entry.
- **Pointer:** `internal/orchestrator/launch/launch.go` (the corrected comment, with the retraction inline), `internal/fileutil/fileutil.go:144-149` (`WriteFile`), `internal/fileutil/durable.go:25` (`AtomicWriteFile`), `internal/orchestrator/lifecycle/runtimeconfig_patch.go:47`, `docs/contributors/backend-idiosyncrasies.md` (Docker Desktop stale-content entry).

It does not converge after 60 s, and a freshly spawned guest process reads the same fabricated bytes, so this is the guest kernel's page cache for that dentry rather than anything per-process.
- **The remedy is narrower than it looks, which is why this is HIGH and not MEDIUM.** Tested candidates: a **new filename works**; `rm` on the host followed by recreating the same name **does not**; a further `files put --overwrite` **does not**. Both failures still return the *original* file's bytes after the path was unlinked and rewritten twice with different content and lengths — the stale mapping survives unlink. So there is no host-side write sequence that repairs a poisoned name, and `--overwrite` is unfixable at that path by construction; the fix has to change the name, or the guest has to drop its cache. *(The last clause is the one that turned out to be the fix: the guest drops its cache.)*
- **Control:** the identical CLI sequence on apple `container` returns the new content. tart-specific.
- **RETRACTED — the write-pattern lead was wrong, and this repo already held the measurement that refutes it.** This entry previously said the fix was to "have `files put` write a new path and move it into place". The spike's own coherence matrix had already tested exactly that on tart (`results/coherence-tart.txt`: `overwrite_rename` → read **NEVER**, stat **NEVER**), and a direct re-test through the real exchange directory confirmed it: after a temp+rename the guest reports the old bytes **and the old size**, where an in-place overwrite at least updates `st_size`. Shipping that lead would have removed the last signal a guest has that anything changed. The `reset` comparison that produced the lead was not comparable — it changed a file in the **workdir**, and `resetCopyWorkdir` calls `workcopy.Materialize(..., WipeAndCopy, ...)`, which replaces the whole directory, so every path under it is new to the guest. `files/` cannot do that: `clearCacheAndFiles` empties it in place precisely because it is mounted (DF149).
- **Mechanism, now established.** The guest caches file *pages* and never invalidates them on a host write; only attributes refresh, on the ~1 s tick. A file that **grows** looks healthy (bytes past the cached extent are fetched); a file that **shrinks or is rewritten inside a cached page** serves stale bytes clamped to the new size. Independently reported and traced to a guest vnode that is never reclaimed — the guest's vnode table is saturated and idles at a near-zero recycle rate ([augur#135](https://github.com/h1d3mun3/augur/issues/135), which also refutes temp+rename in the same words, and reports read tearing we did not see). Every write pattern tried, with controls: [`results/df175-write-patterns.txt`](research/macos-isolation-spike/results/df175-write-patterns.txt).
- **FIXED 2026-08-03 — verify and repair, not a better write.** No host-side write at an already-read path works, so the guest has to drop its cache. `msync(addr, len, MS_INVALIDATE)` on a `PROT_READ` mapping does it, from inside the guest, with no privilege and no write permission. Both exchange-directory writers — `files put` (`ImportFile`) and `Files.WriteFile`, which is what the MCP file-write tool reaches — now hash what they wrote, hand the digest and the guest path to the backend, and fail if the guest cannot be made to agree. Fixing only the first would have left the path an agent's own tooling uses still delivering fabricated content; the shape-grep that rule 7 asks for found that one late, after the first fix had already been written. Two properties are measured rather than assumed, and neither is in the upstream write-up: the host's hash is the only safe stop condition (in the grow case the guest's *size* was already correct and the first pass produced a settled-looking wrong hash), and **the retry must cross a process boundary** (four passes inside one guest process did not converge what one pass in a fresh process did). `runtime.GuestFileRefresher` + `BackendCaps.HostWritesNeedGuestRefresh`; tart implements it, a conformance case pins the pair.
- **Still true, and worth keeping:** a name the guest has never read is always delivered correctly, which is why the check runs only on a replacement; and a restart clears the poisoning (verified), which is what the error message tells the user to do when the repair fails.
- **What makes it nasty rather than merely wrong.** Every layer reports success. The host wrote the bytes, the copy returned 0, the guest's `stat` shows the new size, and the guest's `read` returns without error. There is no failure signal anywhere for a diff or an agent to notice — the agent simply operates on content that never existed.
- **Still not established.** Whether the poisoning is per-dentry or per-inode; whether unmounting/remounting the share clears it. A **restart does** clear it (measured), and `reset` does **not** reproduce it — but for a reason that says nothing about `files put`, see the retraction above.
- **Residual gap — CONFIRMED on hardware 2026-08-04, through the shipped CLI.** The check runs when an import *replaces* an existing entry. A `files rm` followed by a `files put` of the same name is not a replacement by that test, yet the guest may well have read the path before the `rm` — poisoning survives unlink. Measured: after `files put` (20 bytes), a guest read, `files rm`, and `files put` of the same name (5 different bytes), the tart guest served **the whole original file** — content `AAAAAAAAAAAAAAAAAAAA` at `stat` size **20** — while the host held `QQQQQ`. Note this is a *different* shape from the replacement case above, where the guest served old bytes clamped to the **new** size: rm+put leaves a wholly stale view rather than a truncated one. apple ran the identical sequence correctly (`QQQQQ`, size 5), so it is tart-specific like the rest of DF175. Controls in the same run: the raw mechanism reproduced, the shipped repair still fixed a true replacement, and a never-read path landed correctly — so the result is not "the harness cannot read the guest". Harness and raw output: [`df175_rmput.sh`](research/macos-isolation-spike/df175_rmput.sh), [`results/df175-rmput-tart.txt`](research/macos-isolation-spike/results/df175-rmput-tart.txt), [`results/df175-rmput-apple.txt`](research/macos-isolation-spike/results/df175-rmput-apple.txt).
- **The obvious fix was built and measured, and it is a NET REGRESSION. Do not re-attempt it.** `ImportFile` gates the repair on `res.Replaced` (`internal/orchestrator/engine_files.go:37`), and since guest staleness does not depend on whether the host path existed a moment ago, removing that gate looks like the fix. It was implemented and A/B'd on hardware, fresh sandbox per arm:

  | probe | gate removed (the "fix") — [`df175-rmput-gate-removed.txt`](research/macos-isolation-spike/results/df175-rmput-gate-removed.txt) | gate kept (shipped) — [`df175-rmput-tart.txt`](research/macos-isolation-spike/results/df175-rmput-tart.txt) |
  | --- | --- | --- |
  | P2 — guest **had** read the path | REFUSED: `put exit code 1`, guest reads `<empty>` | SILENT CORRUPTION: `put exit code 0`, guest serves the original 20 bytes |
  | P3 — guest had **never** read it | **FAILS: put exits non-zero, run aborts** | passes: `guest reads the NEW bytes QQQQQ` |

  **The repair digests the file by reading it in the guest, and that read caches the path.** So an unconditional refresh poisons every path it touches: P3's never-read path — safe under the shipped gate — becomes cached at first put, and the later rm+put is then unrepairable. The fix manufactures the precondition for the defect it is trying to catch. Note the existing code already says why the gate is there and it is a correctness argument, not a cost one: `refreshGuestView`'s docstring reads *"a guest that has never read the path is never served stale content"* (`internal/orchestrator/engine_files.go`). That sentence is the whole reason the gate must stay; it was read as an optimisation and is not.
- **And the staleness is not repairable by invalidation anyway.** In the gate-removed arm the refresh *did* run on the rm+put and still failed, after all three passes and a full second `files put`. `msync(MS_INVALIDATE)` cannot fix a path whose dentry still resolves to the unlinked inode — the invalidate-and-rehash keeps operating on the old one. This is what the original spike recorded and this entry read past: *"host rm + recreate same name → AAA, DOES NOT WORK"* (`results/df175-files-put-corruption.txt`, CANDIDATE FIXES). Any fix that only adds more repair effort on the put side is chasing a repair that cannot work.
- **The rm-time fix was built and measured, and it does NOT work. Do not re-attempt it either.** The idea was sound on paper: the problem is created by the unlink, so act there — make `files rm` have the guest enumerate the parent directory, dropping the deleted name, so the later put lands on a name the guest has never seen. Implemented as `runtime.GuestDentryDropper` with a tart implementation, wired into `Engine.RemoveFile`, and measured on hardware. The rm+put still served the original 20 bytes.
  **Two measurements say why, and the second retires the idea rather than the implementation.** First, after a plain `files rm` the guest *already* behaves correctly without any help: `readdir` no longer lists the name and `cat` returns empty. Second, the same is true with the mechanism removed entirely — so the enumeration added nothing that was not already happening. The name was never the thing that survived. **What survives is the page cache for the vnode, and recreating the name re-associates it**, which is consistent with the guest vnode never being reclaimed ([augur#135](https://github.com/h1d3mun3/augur/issues/135)). Dropping a dentry cannot evict pages.
  The mechanism was reverted rather than left in place: a no-op that looks like a safety feature is worse than an absent one, because the next reader trusts it.
  **A predicate trap worth carrying forward.** The first probe of this used `[ -e path ]` in the guest and reported the name still present after `rm` — which reads as "the drop failed". It is a `stat`, and the coherence matrix records `stat` on a deleted tart path as **NEVER** converging. The name had in fact gone from `readdir`. Measuring the wrong predicate produced a confident wrong answer about a mechanism that was, separately, also not working.
- **Apple documents this as unsupported, which reframes the whole finding.** The Virtualization.framework virtiofs limitations table ([Apple Developer Forums thread 828366](https://developer.apple.com/forums/tags/virtualization/?page=2&sortBy=newest), open Feedback [FB22905515](https://feedbackassistant.apple.com/feedback/22905515)) lists **"Modify file in place, Host → Guest"** as **not supported** — *"Guest keeps stale contents for already-accessed files (macOS virtiofs caching)"* — and **"Delete file/folder, Host → Guest"** as **not supported** — *"Guest still sees the path after the host deletes it (cached)"*. Creating a **new** path is supported. So this is not a defect yoloAI can repair; it is a platform contract, and the residual gap sits squarely in its unsupported column. That is what makes refusal the right shape rather than a workaround: the supported operation is "use a name the guest has not seen".
  **One caution: Apple's table recommends temp+`rename()` as the way to update a file from the host, and that is refuted by two independent measurements** — this spike's own matrix (`overwrite_rename`: read NEVER, stat NEVER) and [augur#135](https://github.com/h1d3mun3/augur/issues/135) (*"Atomic replace tested and refuted: rename() produced identical staleness plus EOF clamping"*). Do not adopt it on the strength of the table.
- **The one untried mechanism with evidence behind it: bounded vnode reclaim.** augur#135 measured staleness persisting **904.9 s** across 171 polls, and content going fresh **10.3 s after a deliberate vnode-reclaim burst** — 860 vnodes recycled naturally in a 30-minute window. That is eviction rather than invalidation, and it explains both of this project's results: `msync(MS_INVALIDATE)` works on an in-place overwrite because the vnode still exists to be mapped, and cannot work on rm+recreate because the retained vnode is re-associated with the new name. It is the only mitigation anyone has shown to restore freshness without a reboot. **Not attempted here** — it means deliberately pressuring the guest's vnode table, augur reports no established safe bound, and a mechanism that works by inducing cache pressure needs its own risk assessment before it goes near a shipped command. Filed as the successor direction: [`macos-virtiofs-vnode-reclaim.md`](plans/macos-virtiofs-vnode-reclaim.md).
- **Shipped for v0.11.0: refusal, not repair.** `files put` declines to recreate a name removed while the guest was running, naming both remedies. See that plan for why the alternative was deferred.
- **Reproducing it seems to need a warmed guest, and that observation is weaker than the rest of this entry.** Across this session P0 aborted on two freshly created sandboxes and reproduced on sandboxes already in use — but the harness aborts rather than logging, so **no artifact records the two non-reproductions**; it is a recollection, not a measurement. It is consistent with the vnode-saturation mechanism this entry cites ([augur#135](https://github.com/h1d3mun3/augur/issues/135)), which is why it is written down at all. Treat it as a hint for whoever reproduces this next, not as a property. What is solid either way: a clean P0 does not license reading P2, and the harness refuses rather than reporting a vacuous pass.
- See [DF181](#df181--the-df175-repair-gives-up-inside-one-revalidation-tick-so-files-put-fails-on-a-guest-that-is-about-to-be-correct) before relying on the repair itself.
- **Pointer:** `runtime/tart/tart.go:736-739` (the `--dir` shares), `internal/orchestrator/lifecycle/runtimeconfig_patch.go:32` (a live host-side rewrite of a shared file), `docs/contributors/design/research/macos-isolation-spike/` (harness).

Neither wholly old nor wholly new. - **The repair already exists.** `runtime.GuestFileRefresher` (DF175) is path-based and tier-agnostic — `guestPathFor` already maps the `ro` tier as well as `rw`, and the repair was verified against this very workspace file. Whatever flow needs it can call it; nothing new has to be invented.

### DF177 — `yoloai files put --overwrite <dir>` nests the directory instead of replacing it

- **Discovered:** 2026-08-03, by a test written for DF175 · **Workstream:** file exchange
- **Severity:** MEDIUM (silent; `--overwrite` does not overwrite)
- **Disposition:** FIXED 2026-08-04 — an existing directory is removed before the copy, so `--overwrite` replaces rather than merges. `docs/BREAKING-CHANGES.md` carries the entry. **Read the tart consequence below before assuming this is free.**
- **Rides:** **breaking** — changing it converts a merge into a replace, which is a user-visible behaviour change and needs a BREAKING-CHANGES entry.
- **Description:** `ImportFile` copies with `cp -rp src dst`. When `dst` already exists **as a directory**, `cp` copies `src` *inside* it rather than over it. So a second `files put --overwrite somedir` produces `files/somedir/somedir/...` while `files/somedir/*` keeps the **old** content, and the command exits 0. Verified through the shipped CLI: after re-putting a `bundle/` whose files had changed, the host held both `bundle/a.txt` (old) and `bundle/bundle/a.txt` (new). For single files `cp` truncates in place, so only the directory case is affected.
- **How it surfaced, which is the useful part.** A DF175 test asserted that re-importing a directory verifies exactly the files it placed, and got four paths where two were expected. The DF175 repair was working correctly — it faithfully verified the tree the host actually had. Had that test hardcoded the two expected names, it would have pinned the nesting as intended behaviour, which is the trap AGENTS.md rule 10 names.
- **Not fixed here** because it is not DF175 and the fix changes semantics: removing `dst` before the copy turns a directory merge into a replace. Someone may rely on the merge, so it wants its own decision and its own BREAKING-CHANGES entry.
- **The fix costs something on tart, and it is DF175's fault rather than this one's.** Replacing a directory means unlinking it, so on tart a directory re-import IS the rm+put shape [DF175](#df175--yoloai-files-put---overwrite-silently-delivers-fabricated-content-to-a-running-tart-sandbox-and-nothing-short-of-a-new-filename-clears-it) cannot repair. Measured: with the guest having read the tree, the second `files put --overwrite <dir>` now **fails** — `put exit code 1`, naming a restart as the remedy — where it previously exited 0 having nested a copy and kept the old content. That is a loud wrong-state instead of a silent one, and the user has a remedy, so it ships; but it is a usability regression on tart specifically and should be revisited when DF175's residual gap closes. A **single-file** overwrite is unaffected and deliberately so: `cp` truncates in place, keeping the inode, and `TestImportFile_SingleFileOverwriteKeepsTheSameInode` pins that — unlinking single files would manufacture the same hazard on the ordinary path.
- **Pointer:** `internal/orchestrator/files.go` (`ImportFile`, `copyTree`), `internal/orchestrator/engine_files_test.go` (`TestImportFile_DirectoryOverwriteReplacesRatherThanNesting`, `TestImportFile_SingleFileOverwriteKeepsTheSameInode`).

### DF178 — apple's vmnet bridge is created by the first container, not by the system service, so the injector is unbindable on a fresh host

- **Discovered:** 2026-08-03, while giving apple the net-health probe DF172 asks for · **Workstream:** isolation / macOS
- **Severity:** LOW, revised down 2026-08-04 from MEDIUM. The feared consequence — silent degradation to direct key delivery — **does not occur**, measured end to end. What remains is a false claim in a comment that invites reintroducing it.
- **Disposition:** FIXED 2026-08-04 as to the false claim (`runtime/apple/reach.go` now says what was measured). The degradation path itself was never reachable on ordinary timing, so there is no behaviour change to make.
- **Rides:** **any.**
- **Description:** `runtime/apple/reach.go:31-37` states that "the shared vmnet bridge persists while the `container` system service runs, so the gateway is host-bindable **BEFORE any of our VMs is created** — the broker can start the injector ahead of the sandbox, independent of the launch path." The second half is false. Measured on macOS 26.5.1:

  | host state | `192.168.64.1` assigned to an interface? |
  | --- | --- |
  | `container system start`, no container ever started | **no** |
  | a container running | yes |
  | that container stopped again | yes (the bridge survives the container) |

  So the bridge is created by the **first container start** and persists afterwards. "Persists while the service runs" is right once something has created it, and wrong for the window the comment specifically relies on.
- **Why it matters.** `InjectorReach` returns `ErrInjectorUnsupported` when the gateway is assigned to nothing, and the documented consequence is that "brokering safely degrades to direct delivery" — the agent's API key is handed into the sandbox instead of being kept host-side. The comment frames that as covering an exotic case (the service stopped, or never run). It actually covers a routine one: **the first sandbox created after a reboot, or after any `container system start`**. Whether a real `yoloai new --broker` on a fresh service degrades has not been run end to end — that is the one experiment this finding needs, and it decides the severity.
- **Measured end to end 2026-08-04, which is the experiment this finding asked for: brokering does NOT degrade.** On a freshly started service with the gateway confirmed unassigned, both an explicit `--broker` and the default path created a sandbox with a live `host/injector.json` — the key stayed host-side. The reason is ordering: the reach check runs *after* the container exists, and creating that container is what brings the bridge up. **So the saving grace is sequence, not the property the comment asserted** — anything that starts the injector before the first container re-opens the degradation, which is precisely what the old comment invited. Raw output and the two void runs: [`results/df178-broker-fresh-service.txt`](research/macos-isolation-spike/results/df178-broker-fresh-service.txt).
- **Two void measurements preceded it, and the second is the cautionary one.** The first sampled `env` inside a fresh `container exec` shell, which does not reproduce the agent process's environment. The second used the right signal (`injector.json`) but ran on a host with **no credentials at all**, so both arms reported "delivery went DIRECT" — which reads exactly like the feared finding and is instead nothing to broker. A positive control caught it: `--broker` with the bridge *up* also produced no injector.json, which cannot be right. Re-run with a dummy credential exported, the control passed and the real arms answered.
- **Not established:** how long the bridge survives with no containers (it outlived a stop here, but not measured across a service restart), and whether creating any container — not just a yoloAI one — is enough to bring it up. Both are cheap on this hardware.
- **Pointer:** `runtime/apple/reach.go:31-37` (the claim), `runtime/apple/reach.go:78-95` (`ipAssignedToHost`), `runtime/apple/netcheck.go` (the probe that made the host state visible).

### DF179 — `--network-isolated` grants the sandbox `NET_ADMIN` on three of the four backends that support it, so the agent can flush its own allowlist

- **Discovered:** 2026-08-03, scoping the macOS `pf` decision · **Workstream:** isolation
- **Severity:** MEDIUM (a security guarantee that holds on one backend and reads as if it holds on all)
- **Disposition:** UNRESOLVED — user-facing wording corrected 2026-08-03; the mechanism is unchanged
- **Rides:** **any** for the docs half (done). Closing it on a backend is additive; **breaking** only if a backend's advertised `NetworkIsolation` is withdrawn.
- **Description:** `buildInstanceConfig` grants the agent container `NET_ADMIN` whenever `NetworkMode == "isolated" && caps.NetworkIsolation && !sidecarFirewall` (`launch.go:1040`). `sidecarFirewall` requires **both** `NetnsSidecarRunner` and `AgentFreeLaunch`, and each is implemented by exactly one backend: docker. So on **apple, podman and containerd** the sandbox installs its own allowlist and keeps the capability needed to remove it. Measured on apple: a guest holding `NET_ADMIN` flushed its own rules and a destination its allowlist had blocked became reachable. - **Why it deserves its own entry rather than living in the plan.** The plan tracks *building* tamper-resistant isolation; this tracks what the product currently *promises*. Those diverged: `docs/GUIDE.md` told macOS users network isolation "works the same as on Linux", which is true of the enforcement point and false of the guarantee, and no user-facing surface distinguished the two. A gap that is accurately recorded in a design plan and inaccurately described in shipped help is still a gap.
- **Corrected 2026-08-03 (docs only).** `yoloai help security` now states where the allowlist is enforced per backend and what it is worth; the `--network-isolated` flag help says "tamper-resistant on docker only"; `GUIDE.md`'s apple section says the sandbox holds `NET_ADMIN`. Dropping `CAP_NET_ADMIN` does hold — a bounding-set drop is inherited across `sudo`, and netlink stayed refused in every arm — so the sidecar mechanism is not defeated and the remedies above are still worth building. What they do not reach is the **residue**, which is unbounded by construction: 763 of 780 writable `/proc/sys/net` knobs behind ordinary root ([`proc-sys-net-census.txt`](research/macos-isolation-spike/results/proc-sys-net-census.txt)), and every file in the image rewritable including the toolchain a re-install would invoke ([`tamper-persistence.txt`](research/macos-isolation-spike/results/tamper-persistence.txt)).
- **Which makes the table's one clean row wrong too.** This entry reads as "tamper-resistant on docker, weak on the other three". It is not: `firewall.py` installs **IPv4 rules only** and says so in `parse_nameservers`' own docstring, while a root agent can re-enable IPv6 via `disable_ipv6` — measured, and carried through to a defeated allowlist in [`ipv6-sidestep.txt`](research/macos-isolation-spike/results/ipv6-sidestep.txt). So on docker the sidecar closes the *flush* vector and the sysctl vector walks around the result through a family the firewall never filtered. At the adversarial-agent level the guarantee holds on **zero** backends; what the sidecar buys is a genuinely better confused-agent guarantee, which is worth having and is not what the shipped text says.
- **And it is shipped text, not just this entry, so the correction is user-facing.** `yoloai help security` is careful and mostly right — it splits the backends by who holds `NET_ADMIN`, and it has a whole paragraph headed `IPV6 IS NOT FILTERED`. It also contains one sentence the measurement refutes: of the docker case, *"This is the case the allowlist actually contains a hostile agent."* It does not. The two disclosures are true separately and are never connected, and the connection is the bypass: an agent that cannot flush the v4 rules can still turn IPv6 **on** and leave through it. The IPv6 paragraph frames v6 as a property of the user's network — *"if your guest has routable IPv6"* — which reads as a condition the user is in a position to know about, when the agent can create it. Same for the closing advice, `--network-none`, which is sound only because it removes the interface rather than filtering it.
- **What this changes about closing it.** Per-backend enforcement-point placement is no longer the frame. Enforcement's job is to reduce the guest to a single destination and move policy to a host-side proxy the agent has no privilege over — [D137](../decisions/working-notes.md), with the mechanism under measurement in [proxy-chokepoint-verification-round.md](../archive/plans/proxy-chokepoint-verification-round.md). The cheaper partial below survives the reframing unchanged and is arguably more urgent under it.
- **A cheaper partial worth considering separately:** refuse `--network-isolated` on the in-guest backends unless the caller passes something like `--network-isolated=best-effort`. That converts a silent weak guarantee into an explicit one, costs no new mechanism, and is a breaking change to a shipped flag — which is why it is named here rather than done.
- **Pointer:** `internal/orchestrator/launch/launch.go:1040` (the grant), `internal/orchestrator/launch/launch.go:301` (`UsesSidecarFirewall`), `internal/netpolicy/strategy.go:42` (tart/seatbelt are refused outright, not silently unenforced), `internal/cli/helpcmd/help/security.md`, `docs/GUIDE.md`.

### DF180 — apple's `Inspect` reports "not found" for a daemon it cannot reach, so `destroy` claims success and leaks the container

- **Discovered:** 2026-08-04, staging round 2 of the macOS reboot test · **Workstream:** isolation
- **Severity:** MEDIUM (destroy reports work it did not do, and the sandbox becomes an orphan the store no longer names)
- **Disposition:** FIXED 2026-08-04, **both backends**. apple's `Inspect` now discriminates on the daemon's own message and `Remove` no longer concludes "already gone" from a failure to ask; tart's `vmState` returns an error instead of `""` when the inventory cannot be read. The discriminator was measured rather than guessed — the two cases share an exit code and differ only in text ([`results/apple-daemon-states.txt`](research/macos-isolation-spike/results/apple-daemon-states.txt)). An unrecognised message deliberately does NOT read as not-found, so a future rewording degrades to a noisy error rather than back to a silent leak. `docs/BREAKING-CHANGES.md` carries the entry: `ls` and `destroy` now fail where they previously returned a wrong answer.
- **Rides:** **any** for the `Remove` half — it is a bug fix with no interface change. The `Inspect` half is likelier **breaking**: today a stopped daemon renders every apple sandbox `removed`, and a correct implementation surfaces an error there instead, which is a new failure on a command that currently succeeds.
- **Description:** `runtime/apple/apple.go:289-292` maps **every** `container inspect` failure to `runtime.ErrNotFound`, discarding the error. Two things follow, and both were reproduced deliberately by stopping the daemon under a live sandbox rather than inferred from a symptom:
  - `internal/orchestrator/status/status.go:235-237` turns `ErrNotFound` into `StatusRemoved`. So with `container system stop`, `yoloai ls` reports an intact, merely-stopped sandbox as `removed`. That call site is *correct* — it distinguishes `ErrNotFound` from other errors and wraps the rest. The conflation happens one layer down, which is why the right-looking code above it cannot help.
  - `runtime/apple/apple.go:277-281` treats `delete` failing plus `Inspect` saying not-found as "already gone" and returns nil. With the daemon down, `yoloai destroy df-probe` printed `Destroyed df-probe`, exited 0, and removed the store entry — while `yoloai-cli-df-probe` was still there when the daemon came back. `yoloai system prune` does find it, so it is recoverable, but only by someone who suspects it happened.
- **Why this is not an exotic edge.** The apple `container` service is **not registered with launchd** (`container system status` after a reboot: *"apiserver is not running and not registered with launchd"*), so it is down after every restart until something starts it. A user who reboots and runs `yoloai destroy` hits the leak on the ordinary path — no unusual state required. It also invalidated a reading in this project's own research: round 1 of the reboot test recorded both apple sandboxes as having come back `removed` and drew a conclusion about reboot recovery from it, when the sandboxes were fine and the daemon was down (`research/macos-isolation-spike/results/README.md`).
- **The convention already exists on sibling paths, which is what makes this a defect rather than a design gap.** `runtime/docker/docker.go:680-686` checks `cerrdefs.IsNotFound(err)` and wraps everything else; `runtime/containerd/lifecycle.go:890-897` does the same with `errdefs.IsNotFound`. Two backends discriminate, two use a sentinel that cannot: apple as above, and `runtime/tart/tart.go:514-518` via `vmState`, which returns `""` both for "no such VM" and for `tart list` failing outright (`tart.go:851-862`). So the fix direction is to make apple and tart match the two that are already right, not to invent a mechanism.
- **What would close it:** apple's `Inspect` distinguishing "the daemon said no such container" from "I could not ask", and `Remove` refusing to conclude already-gone from the second. Same for tart's `vmState` sentinel. A `runtime/runtimetest` conformance case — daemon unreachable, assert `Inspect` does **not** return `ErrNotFound` — would pin it for every backend at once, which is the shape D128/D129 ask for and no fake can satisfy.
- **Pointer:** `runtime/apple/apple.go:276-292`, `internal/orchestrator/status/status.go:233-241`, `runtime/tart/tart.go:514-518` and `:851-862`, against `runtime/docker/docker.go:680-686` and `runtime/containerd/lifecycle.go:890-897`.

### DF181 — the DF175 repair gives up inside one revalidation tick, so `files put` fails on a guest that is about to be correct

- **Discovered:** 2026-08-04, running the harness that confirmed DF175's residual gap · **Workstream:** tart / host-guest sharing
- **Severity:** MEDIUM — no data is corrupted (the host side is written correctly and the guest converges), but a shipped command exits non-zero on a healthy sandbox and tells the user to restart it. Measured **2 failures in 5** consecutive attempts on a clean sandbox ([`results/df181-timing.txt`](research/macos-isolation-spike/results/df181-timing.txt), trials 3 and 4).
- **Disposition:** FIXED 2026-08-04 — `runtime/tart/guestrefresh.go` now waits `guestRefreshSettle` (1.1 s, deliberately longer than the ~1 s tick) before each retry pass, leaving the first pass immediate so an already-current path still costs one check and no delay. **Verified on hardware: 12 consecutive replacements with zero `STALE` verdicts** ([`results/df181-timing-postfix.txt`](research/macos-isolation-spike/results/df181-timing-postfix.txt)), against 2 failures in 5 before ([`results/df181-timing.txt`](research/macos-isolation-spike/results/df181-timing.txt)). At the pre-fix rate of 40%, twelve clean runs would occur about 0.2% of the time. Kept here rather than moved to the resolved sink because the entry it depends on ([DF175](#df175--yoloai-files-put---overwrite-silently-delivers-fabricated-content-to-a-running-tart-sandbox-and-nothing-short-of-a-new-filename-clears-it)) is still open and this describes the same repair.
  **The acceptance evidence very nearly did not exist.** The first post-fix runs were printed to a terminal and never written to a file, while the fix commit re-ran the harness and overwrote the *pre*-fix artifact the mechanism analysis cites. For a while this entry claimed a verified fix backed by nothing in the repository. The two runs now live under separate filenames for that reason, and the harnesses in this directory rewrite in place — see `results/README.md`.
- **Rides:** **any.** A timing fix inside the existing repair; no interface changes.
- **Description:** `yoloai files <box> put <f> --overwrite` over a path the guest has already read fails with:

  > `<f> was written to the exchange directory, but the sandbox still reads stale content for <f> and it could not be refreshed; the sandbox would act on content that never existed. Restart the sandbox (…) to clear it`

  The claim in that message is false at the time it is printed. The host side *is* correct, and the guest converges to the correct content on its own within seconds — verified by re-reading the same path afterwards, with no restart and no further `put`. So the command reports unrecoverable staleness for a condition that heals itself, exits non-zero, and prescribes a sandbox restart.
- **What the retry already does, because the obvious diagnosis is wrong.** `runtime/tart/guestrefresh.go:158` loops `guestRefreshAttempts = 3` times, and each attempt is a separate `ExecRaw` — a **fresh guest process** that `msync(MS_INVALIDATE)`s the path and re-digests it. That is deliberate and hardware-grounded: `guestrefresh_test.go:144-148` records that a 20-byte file grown to 256 KiB "stayed wrong after four invalidate passes inside one guest process and came back correct after one pass in a fresh process". So the remedy the design was built around is already being applied, three times, and the guest still reports `STALE` — which is what makes this worth filing rather than tuning.
- **Mechanism — SETTLED 2026-08-04: the verdict is premature, and the invalidation is fine.** Two explanations survived the first observation and implied different fixes: the re-digest reading too early (delay), or three passes genuinely not being enough (raise the bound). They are separated by one question — after a failed put, three invalidation passes have *already run*, so does the guest become correct **on its own**, with no further put and no further pass? Measured over 5 trials: 2 reported `STALE`, **both self-healed while idle with no further passes, and none needed more**. So the invalidation had already worked and only the verdict was wrong. Raising `guestRefreshAttempts` would not fix this and would spend more guest execs to reach the same wrong answer.
- **What the guest actually holds at the moment of the verdict is not stale content — it is nothing.** Both failing trials read `<empty>` from the path when the repair declared it stale, then read the correct bytes seconds later. So the sequence is: `msync(MS_INVALIDATE)` drops the cached pages, the path transiently reads empty, the re-digest in that same invocation hashes that transient state, it does not match, and the pass reports `STALE`. The error message's claim — "the sandbox still reads stale content" — is wrong in both halves: it is not stale, and it is not what the guest will read a moment later. The relevant clock is tart's **~1 s quantised revalidation** ([backend-idiosyncrasies.md](../backend-idiosyncrasies.md)), and three undelayed passes fit inside one tick.
- **The control is what licenses reading that.** In the same run, a replacement written **directly** into the share — never repaired, no pass ever run — was still stale after the identical wait. So "it self-healed" is attributable to the repair passes rather than to the guest being coherent that day, and DF175 was live on this guest throughout. Harness and raw output: [`df181_timing.sh`](research/macos-isolation-spike/df181_timing.sh), [`results/df181-timing.txt`](research/macos-isolation-spike/results/df181-timing.txt).
- **Evidence.** [`results/df181-timing.txt`](research/macos-isolation-spike/results/df181-timing.txt): five consecutive replacements over a path the guest had read, of which trials 3 and 4 returned `rc=1` with the message above. Both had the correct bytes on the host, both read `<empty>` from the guest at the moment of the verdict, and both read the correct bytes after three idle seconds with no further pass. Its P0 control — a replacement written directly into the share and never repaired — was still stale after the identical wait, so the self-healing is attributable to the repair rather than to a coherent guest.
- **What would close it:** re-digest **after** the invalidation has had a tick to land, rather than in the same breath as it. Roughly half the observed ~1 s interval between a pass and its verification is what the measurements justify; the existing `guestRefreshAttempts = 3` structure can stay, since the failures are not attempt-starved. Note the fix is a delay *before re-reading*, not merely between attempts — a later attempt that still hashes immediately after its own `msync` reproduces the same premature read.
- **A fake cannot certify the fix, and must not be used to.** `runtime/tart/guestrefresh_test.go` drives a scripted fake guest and asserts invocation counts (`invocationCount(t, argvLog)`), which is the right shape for "did it retry" and is structurally incapable of reproducing a timing effect against a real revalidation clock — a fake that returns `OK` on the second call proves the loop retries, not that the loop outlasts the tick. That is D129's dead-path trap exactly. A unit test can pin that a delay is *requested*; only hardware shows it is *enough*, and [`df181_timing.sh`](research/macos-isolation-spike/df181_timing.sh) reproduces the failure in about a minute against an existing sandbox, so the fix has a cheap acceptance check.
- **Relationship to DF175.** This is a defect in DF175's *fix*, not in the behaviour DF175 describes. The fix's design choice — fail loudly rather than exit 0 over content the agent cannot see — is right, and this does not argue against it; it argues that the verdict is being taken too early to be true.
- **Pointer:** `runtime/tart/guestrefresh.go:20-26` (the attempts constant and its doc), `:28-48` (the settle constant), `:158-163` (the loop, now delayed), `internal/orchestrator/engine_files.go:37-41` (the caller that turns a stale verdict into a command failure).

- **Discovered:** 2026-08-05, by `make smoketest` on the release branch (7 of 22 tiers failed, all podman) · **Workstream:** sandbox-share-tiering / release
- **Severity:** HIGH. It broke the podman backend outright under the only invocation the release gate uses, and the release could not have been cut on it.

- **Why only podman, which is the part worth keeping.** `make smoketest` escalates with `sudo -E`, and `-E` preserves `XDG_RUNTIME_DIR`, so **root's yoloAI drives the invoking user's rootless podman socket**. The daemon runs as that user and cannot traverse a root-owned `0750` directory, so it could not see that the bind source existed, concluded it was missing, and tried to create it. Docker's and containerd's daemons run as root and never noticed. The mixed-privilege shape is exactly what `Makefile`'s `releasetest` comment already warns about for the podman tier — the warning was about running the *gate* under sudo, and the same seam bit from the other side.
- **The fix.** `MkdirAll` now collects the missing ancestors **before** creating (so a directory that already existed is never re-owned) and chowns each one it conjured; the leaf chown stays unconditional, preserving existing behaviour. The three tiers are also named explicitly in `createSandboxDirs`, because a tier that exists only as some other call's intermediate is a tier whose permissions and ownership nothing states. Verified end to end: `sudo -E yoloai new --backend podman` reproduced the failure, and after the fix all three tiers are owned by the invoking user and the sandbox runs.
- **The forest is small, checked (rule 7).** All production code goes through `fileutil.MkdirAll`; the only direct `os.MkdirAll` callers are five test fixtures. So the primitive fix covers the class rather than one path.
- **What this says about the gate.** `make check` cannot reach this — it needs a real backend, root, *and* a rootless daemon owned by another uid. Only `smoketest` has that combination, which is the argument for running the full matrix before a tag rather than trusting a green `make check`. It is also the second finding this release where the defect lived in the *seam between* privilege domains rather than in either side.
- **Pointer:** `internal/fileutil/fileutil.go` (`MkdirAll`, `missingAncestors`), `internal/orchestrator/create/create.go` (`createSandboxDirs`), `store/paths.go` (`ReadOnlyTierPath`, `ReadWriteTierPath`), `Makefile` (`smoketest` sudo escalation).

- **Disposition:** RESOLVED 2026-08-05 — the version is pinned in both places, and the seven scripts were rewritten to pass on every version.
- **Rides:** **any.**
- **What happened.** Seven macOS research scripts guard on `[ -n "$A_IP" ] && [ -n "$B_IP" ] || { echo …; exit 2; }`. CI reported SC2015 on all seven and exited 2; `make check` on the same tree exited 0. Both were telling the truth. **shellcheck 0.11.0 narrowed SC2015**; the CI runner's preinstalled shellcheck is 0.10.x, and the `Makefile`'s container fallback pulled `koalaman/shellcheck:stable`, which is 0.11.0. Measured directly rather than inferred: on the pre-fix tree, `v0.9.0` and `v0.10.0` each exit 1 with 8 SC2015 hits, and `stable` exits 0 with none.

- **Related.** The `shellcheck` target's own comment block already warned that local and CI can disagree — but only about **scope** (`core.excludesFile` narrowing the file list), and it concludes "CI is the authority when the two disagree". That was written from one instance and generalised to the wrong axis: the divergence that bit was **version**, not scope, and the same sentence covers it only by accident.
- **Pointer:** `Makefile` (`SHELLCHECK_VERSION`, the `shellcheck` target), `.github/workflows/ci.yml` (`Install shellcheck`), `docs/contributors/design/research/macos-isolation-spike/pf_*.sh` and `reboot_pre.sh`.

### DF188 — `resolve_domains` accepts whatever a resolver returns, so a sinkholed allowlist domain installs a rule that matches nothing and says nothing

- **Discovered:** 2026-08-09, while checking whether one-shot resolution is safe for the shipped allowlist (L9b/L9c of the enforcement verification pass) · **Workstream:** isolation / network allowlist
- **Severity:** LOW–MEDIUM. **Not a widening — measured, see below.** It is a silent functional failure: the agent is denied a destination the user explicitly allowlisted, and nothing reports it.
- **Disposition:** PARKED — filed, not fixed. The fix is small but it belongs with the family-aware resolution work rather than as a one-off guard (DF104, [ipv6-network-isolation.md](plans/ipv6-network-isolation.md)).
- **Rides:** **any.**
- **What was measured.** `statsig.anthropic.com` ships in the Claude allowlist (`internal/agent/agent.go:385`). It does not resolve publicly, and the test host's LAN resolver answers **`0.0.0.0`** for it — the standard DNS-blocking answer for a telemetry host. Sampled six times over a minute from inside a sandbox: unresolved every time. `resolve_domains` adds whatever `getaddrinfo` returns, and `is_ipv4("0.0.0.0")` is `True`, so it passes the only filter on a resolved address and reaches `iptables -d`.
- **It is not a hole, and that was checked rather than assumed.** `iptables` normalises `-d 0.0.0.0` to `0.0.0.0/32`, which matches nothing. With it installed as the *only* allowlisted destination and a default-deny `OUTPUT` policy, both `1.1.1.1` and `example.com` stayed blocked (`design/research/linux-enforcement/results/l9c-zero-address-allowlist.txt`). The entry is inert and the failure is closed.
- **The defect is the silence.** An unresolvable domain gets one `network.resolve_failed` log line; a *sinkholed* one gets nothing at all, because from the resolver's point of view it succeeded. So an allowlist entry that can never match looks identical to one that works, and DNS-level blocking is common enough — pihole, corporate filters, NextDNS — that this is not an exotic configuration. Any domain a user's resolver sinkholes silently stops being allowlisted.
- **A sibling path already solves it, loudly (rule 7).** `parse_nameservers` in the same file rejects a non-IPv4 nameserver *with a loud log* rather than passing it through, precisely because feeding a v6 address to `iptables -d` used to abort the whole install (DF134). The convention exists in the file; the resolved-address path just does not follow it. So this is a consistency fix, not a new mechanism: reject unspecified, loopback and multicast answers at resolve time and say so at the same volume.
- **Two separable questions, and only the first is this finding.** Whether `resolve_domains` should validate its answers (yes), and whether `statsig.anthropic.com` still belongs in the shipped list at all — `dig @8.8.8.8` returns nothing for it, which suggests the entry may simply be stale. The second is the agent-defaults owner's call, not this finding's.
- **Pointer:** `runtime/docker/resources/firewall.py` (`resolve_domains`, `is_ipv4`, and `parse_nameservers` for the convention it should match); `internal/agent/agent.go:385` (the shipped allowlist).

### DF189 — yoloAI's CNI subnet is byte-identical to podman's default allocator pool, so two sandboxes on one host can hold the same address

- **Discovered:** 2026-08-09, running the collision test an audit found L4 had claimed to exclude while measuring a different network · **Workstream:** isolation / containerd + podman
- **Severity:** MEDIUM today, HIGH for the host-side enforcement design. Two sandboxes with the same address cannot be told apart by any address-keyed policy, and the planned reaper is specified as a **blind** delete-this-address-from-every-table.
- **Disposition:** PARKED — filed, not fixed. The fix is a subnet change (user-visible if anyone has state on the old one) or a move to interface keying; both are decisions, not repairs.
- **Rides:** **any.** Changing the default CNI subnet is a changed default — see [DF184](#df184--breaking-is-measured-against-the-last-published-release-and-that-rule-is-written-down-nowhere) — so it needs a `docs/BREAKING-CHANGES.md` entry when it lands, and it is not gated by `scripts/check_breaking_changes.py`.
- **Measured, on this host** (`design/research/linux-enforcement/results/c1-podman-cni-subnet-collision.txt`). `runtime/containerd/cni.go:44` sets `cniSubnetCIDR = "10.89.0.0/16"`. podman/netavark's first `default_subnet_pools` entry is `{"base" = "10.89.0.0/16", "size" = 24}`. A `podman network create` with **no** `--subnet` — what a user or a script does by default — was allocated `10.89.0.0/24`, and its first container took **`10.89.0.2`**, which is the exact address yoloAI's CNI IPAM currently holds a reservation for (`/var/lib/cni/networks/yoloai/10.89.0.2`). This is not a configured overlap that might one day bite; the same address is claimed by both allocators right now.
- **Two distinct consequences, and the second is the serious one.** (1) Ordinary routing conflict between a yoloAI containerd sandbox and any podman network on the same host. (2) **Address-keyed enforcement cannot distinguish the two sandboxes at all** — one sandbox's policy silently governs the other's traffic, in whichever direction the rules were written. That is the same class as the stale-entry hazard [enforcement-state-reaping.md](plans/enforcement-state-reaping.md) exists to prevent, arriving through a different door and unmitigated by anything in that plan.
- **Why the earlier run missed it.** L4 was written to answer exactly this — its own "Decides:" line reads *"whether two backends on one host can ever hand out the same address, which would make a blind cross-scrub delete a live sandbox's entry"* — and then measured **nerdctl's default network** (`10.4.0/24`) rather than yoloAI's, while the podman row of the same table was empty strings from a broken inspect format. The routing dump three lines below its own verdict prints `10.89.0.0/16 dev yoloai0`.
- **It is an argument for the interface key, not just for a new subnet.** A per-sandbox bridge or veth port distinguishes the two sandboxes regardless of address (K1/K2, `k1-interface-as-sole-key.txt`, `k2-veth-key-shared-bridge.txt`), so the whole class disappears rather than being moved to a quieter subnet.
- **Not measured:** whether the two allocators can be driven to hand out the same address *concurrently* to two live sandboxes (this run showed one live podman container on an address the other allocator has reserved, which is the same hazard but not the same demonstration); and whether yoloAI's own podman backend, which uses an explicit network, is exposed.
- **Pointer:** `runtime/containerd/cni.go:44,77` (`cniSubnetCIDR`, `cniConflistTemplate`); `/usr/share/containers/containers.conf` `default_subnet_pools`; `enforcement-state-reaping.md` rule 1.

### DF190 — an apple sandbox silently loses all egress when an unrelated sandbox restarts and reclaims its vmnet bridge index

- **Discovered:** 2026-08-10, by the macOS agent while establishing whether the interface is a usable enforcement key (I2c) · **Workstream:** isolation / macOS apple backend
- **Severity:** HIGH, **raised 2026-08-11**. The original MEDIUM–HIGH rested on the displacement being recoverable. It is not: a stop/start of the victim **moves the defect** rather than repairing it (`df190-mechanism.txt` D4 — W regains egress and A loses it, the bridge changing hands rather than being rebuilt). Restarting the victim picks a new victim. A running sandbox loses **all** network egress through no action of its own, while `state` still reports `running`, with no error, no log surfaced to the user, and nothing to correlate it with.
- **Disposition:** PARKED — filed, not fixed. Filed on the macOS agent's behalf: it hit the finding but `findings-unresolved.md` is not its write surface, and allocating an ID from there would have raced this one.
- **Rides:** **any.** It repairs behaviour that is already wrong; nothing user-visible is withdrawn.
- **What was measured** (`design/research/macos-isolation-spike/results/pf-interface-key.txt`, I2c; three runs). Sandbox A was running on `bridge101`. A was stopped, releasing the index. A **new** sandbox created inside A's detach window was allocated `bridge101` — the allocator fills holes. A then restarted and came back on `bridge101`. The window sandbox was left **with no bridge at all**: its index changed while it was running and untouched. With **no policy loaded anywhere**, the window sandbox could not reach `1.1.1.1` (000) while A reached it from the same host in the same second (301). Both were `state=running`.
- **It is independent of every keying question, which is why it is filed separately.** The interface-key investigation is what surfaced it, but nothing in the run had a rule loaded. This is the backend reassigning a live sandbox's bridge out from under it. Any enforcement design keyed on *anything* inherits it as a correctness problem, and a design keyed on nothing still has it as a connectivity bug.
- **The mechanism, established 2026-08-11** (`design/research/macos-isolation-spike/results/df190-mechanism.txt`). It supersedes this entry's original "a symptom with no mechanism, stated as such."
  - **It is Apple's, not ours.** D1 reproduces the displacement with **zero rules of ours loaded** and every anchor asserted empty first. Nothing in the enforcement design causes it, and nothing in that design can fix it.
  - **The cause is a network object outliving its last container.** D3's daemon log shows the departing network's vmnet helper *staying alive* across the stop — `released session [allocations=1]`, not a shutdown — and then re-allocating on the same network id when its sandbox returns, onto a bridge index handed out in the meantime.
  - **Demonstrated causally, not inferred from the log.** D5 re-ran the sequence with the network **deleted** while empty so no helper survived: the returning sandbox did not displace the incumbent and both kept egress. Three networks created fresh never collide at all (D0).
- **There is a workaround, and it is ours to apply: delete the network when its last sandbox goes.** That is a yoloAI-side lifecycle change against an Apple-side defect, which makes this actionable despite the ownership.
- **Partial recovery exists but does not address this.** I5b showed that withdrawing a stale interface rule restores correct policy for the *stranger* that took a departed sandbox's index. That is about policy attribution; it does nothing for the displaced sandbox, which has lost its bridge rather than its rules.
- **Not established:** whether it also happens when the incumbent is **busy** rather than idle — both sandboxes in every run were sleeping, and a sandbox holding open connections is the case the product actually has. Nor whether more than one sandbox can be displaced at once. No privileged tracing was done, so the daemon log is whatever Apple chose to emit.
- **Scope:** apple backend only, and unexamined on tart. **Do not repeat this entry's earlier reason** — "tart has no per-sandbox networks" is false (`tart-net-key.txt` T2/T3): tart gives every VM its own `vmenetN` in both shared NAT and Softnet. tart is out of reach for *enforcement* because macOS pf cannot key on a bridge member, which says nothing about whether this displacement occurs there.
- **Pointer:** `runtime/apple/` (bridge/network lifecycle); `design/research/macos-isolation-spike/results/pf-interface-key.txt` I2c and its N1b precondition; `df190-mechanism.txt` for the mechanism, the D4 severity correction and the D5 workaround.

### DF191 — `CanEnforce` asks which isolation mode is named, not what the guest kernel can do, and its own remedy text would misroute a user onto a kernel with no iptables at all

- **Discovered:** 2026-08-11, while evaluating a libkrun-based isolation tier after Docker Sandboxes shipped one · **Workstream:** isolation / netpolicy
- **Severity:** LOW **today**, and the qualifier is the entry. Every VM-class mode we ship is Kata, whose guest runs a stock kernel with `ip_tables` and `ip_set`, so the predicate is accidentally right and nothing is currently broken. It becomes wrong the first time a VM tier's guest kernel is not a stock one.
- **Disposition:** PARKED — filed, not fixed. The fix is a predicate change, and choosing where the capability is declared (guest image metadata vs. backend caps vs. probe-on-first-use) is a decision, not a repair.
- **Rides:** **any.** Correcting a predicate that currently returns the right answer for the wrong reason withdraws nothing user-visible.
- **What `CanEnforce` actually asks.** `internal/netpolicy/strategy.go:39` composes two facts: `caps.NetworkIsolation`, and `runtime.IsolationEnforcesInSandboxIptables(isolation)`. The second is keyed on the **isolation mode's name**. But `StrategyIPFilter` is defined (`strategy.go:19`) as "iptables+ipset rules installed inside the sandbox by entrypoint.py", and `network.go:275` runs `ipset add allowed-domains "$ip"` inside the sandbox — so the property that actually decides enforceability is *"does this sandbox's kernel have xtables and ipset"*, which belongs to the guest image, not to the mode name. gVisor is currently modelled as the one exception; it is better read as the first instance of a class.
- **The remedy text is the sharp end.** When the predicate refuses, the error tells the user: *"Use --isolation=container (default) or a VM-based isolation mode (--isolation=vm or --isolation=vm-enhanced) instead"* (`strategy.go:47-53`). That sentence is a promise about VM modes in general. Against a libkrun-class guest it would route the user from a mode that silently drops the allowlist to one that cannot express it at all.
- **The worked example, and why it is not hypothetical.** libkrunfw's bundled guest kernel (Linux 6.12.91, `config-libkrunfw_x86_64` and `_aarch64`, identical on this point) sets `CONFIG_NETFILTER=y` and `CONFIG_NF_TABLES=y` but leaves **`CONFIG_NETFILTER_XTABLES`, `CONFIG_IP_NF_IPTABLES` and `CONFIG_IP_SET` unset**. `iptables-nft` does not rescue it, because `nft_compat` is unofferable without xtables. This is a harder failure than gVisor's: gVisor accepts the syntax and ignores it, whereas here the modules do not exist. Any future libkrun tier inherits it, which is what makes the fact worth keeping after the option was dropped.
- **The option itself was rejected, on two independent blockers.** (1) **exec is impossible**: crun's krun handler leaves `.exec_func` NULL and `libcrun/container.c:3859` returns *"the handler does not support exec"*; `runtime.Backend` requires both `Exec` and `InteractiveExec` (`runtime/runtime.go:505,514`), so this is an unimplementable mandatory method rather than a degradation. Upstream [crun#2090](https://github.com/containers/crun/issues/2090) is open with nothing merged. (2) the kernel-config finding above. Secondary: `crun-krun` is packaged on Fedora and Arch as a single command but **is not packaged on Ubuntu or Debian at all**, so on the primary Linux target it is a from-source build of libkrunfw + libkrun + crun — worse than the Kata burden it was meant to relieve.
- **The evidence from Docker points away from the handler, not toward it.** Docker Sandboxes does use libkrun (their issue tracker shows a bundled `~/.container-platform/com.docker.krun` and virtiofs mounts in user-pasted output), but ships its **own VMM against the libkrun library** rather than using crun's `krun` OCI handler — and `sbx exec` works. Their bet validates libkrun-the-library; it is evidence against the specific path yoloAI would have taken through podman.
- **Not measured, stated plainly.** No libkrun sandbox was run. The kernel-config and `.exec_func` claims come from reading libkrunfw's shipped config and crun's source, not from observing a failure. That is sufficient for the rejection (both are compile-time facts about shipped artifacts) but it is **not** sufficient to characterise what a libkrun guest *can* enforce via native `nft`, which is unexamined. Also unexamined: whether the host-side netns filtering path (`UsesSidecarFirewall`, `internal/orchestrator/launch/launch.go:301`) would apply cleanly to libkrun's default TSI mode, where the VMM proxies sockets host-side and the guest has no netdev — that is the one route that looked viable and it was not pursued.
- **Pointer:** `internal/netpolicy/strategy.go:19,39,44-53`; `network.go:275` (`ipsetResolveDomainsScript`); `runtime/runtime.go:505,514`; libkrunfw `config-libkrunfw_x86_64`; crun `src/libcrun/handlers/krun.c`, `src/libcrun/container.c:3859`.

### DF192 — the adopted macOS liveness canary asks the guest whether it is contained, so the hostile agent it exists to detect can answer for it

- **Discovered:** 2026-08-11, while deciding where enforcement failures should be detected for the layer-3 build · **Workstream:** isolation / macOS pf
- **Severity:** MEDIUM, and **cheap because nothing is built yet.** It is a defect in a *detector*, not in enforcement: pf itself is host-side and a guest cannot edit it. What a forged canary buys an attacker is the reporting layer — yoloAI says HEALTHY while the sandbox is unenforced, which is the one failure class where nobody goes looking. Caught at design stage, the fix is a different signal; caught after build, it is a rewrite of the verification path plus every claim made on top of it.
- **Disposition:** PARKED — filed against a design, not against code. [`macos-pf-privileged-path.md`](plans/macos-pf-privileged-path.md) § *Candidate: read counters host-side* carries the proposed replacement and the measurement it needs.
- **Rides:** **any.** Nothing user-visible is withdrawn; a detector that cannot be forged replaces one that can.
- **What the canary does.** It flushes the sandbox's allowlist, probes a destination **from inside the guest** via `container exec`, and restores. The plan states the reason plainly: *"from inside a guest, 'pf blocked me' and 'nothing routes' are otherwise identical"* — which is exactly why the probe has to run there, and exactly why the guest is in the trust path.
- **Why that is a problem here specifically.** The threat model this whole workstream targets is stated in [`tamper-resistant-network-isolation.md`](plans/tamper-resistant-network-isolation.md): *a hostile agent with sudo*. A root agent can replace `curl`, shadow it on `PATH`, or intercept the exec'd command, and hand back the exit status and HTTP code that read as HEALTHY. The detector is forgeable by the thing it detects.
- **It is the third unstated property of this canary.** The plan already records two found by audit — it **mutates live policy** so it races every acquisition by construction, and its **restore is unguarded**, so a host dying mid-window leaves that sandbox with an empty allowlist and no egress. Subvertibility was not among them. A detector with three separate ways to be wrong, none of which its own output distinguishes, is a detector to replace rather than repair.
- **Linux does not have this problem, which is the shape of the fix.** There the same class is answered host-side with no guest participation. **Amended 2026-08-12 by verification round 2 — the specific mechanism named here is superseded, the asymmetry is not.** This entry originally proposed comparing a chain's counters against the veth's host-side `rx_packets`. That comparison is now retired as wrong in *both* directions: it reports healthy for an idle sandbox that has lost enforcement, and **inert** for a healthy one whose traffic a foreign higher-priority `drop` is taking first (V6b, measured — our counter froze while enforcement was intact). What replaces it is two subscriptions over disjoint fault classes: `NFNLGRP_NFTABLES` for every ruleset fault, naming our table (V1), and `RTNLGRP_LINK` for the device vanishing, which emits no ruleset event at all because the chain binds by ifindex (V1b, V5). Neither infers enforcement from traffic, so neither has either failure mode. See the build brief's Part 2. **The asymmetry is not a property of pf** — `pf-no-state.txt` reads per-rule counters throughout (`out: 0 -> 17`, `0 -> 7`) using `pfctl -a <anchor> -vvs rules`. It is a property of **D132's grant**, which permits only `-s rules$` and so refuses the verbose read. macOS had to go behavioural because it could not read a number it is perfectly capable of producing.
- **Not established:** whether the grant can be widened to permit the verbose read without admitting anything else. That is a permit/refuse matrix run, not an argument — `pf_grant_matrix.sh` exists and V4's method for testing a refusal without a blanket grant is recorded in `pf-grant-matrix.txt`. Also unmeasured: whether an anchor's counters move usefully under the *pinned-superset* pool shape, where most rules name interfaces that do not exist.
- **The general rule this instance argues for**, and the reason it is filed rather than fixed in passing: **a security control's detector must live on the same side of the trust boundary as the control itself.** Layer 1 put enforcement inside the sandbox and had no choice; layer 3 moves enforcement to the host, and detection should move with it. Anything in-guest is diagnostics and UX — worth having to tell a cooperative user why a destination is refused, never load-bearing for whether yoloAI believes it is enforcing.
- **Pointer:** `design/plans/macos-pf-privileged-path.md` § *Verification must be behavioural* (the canary, its price and its two known properties); `design/research/macos-isolation-spike/results/pf-canary-probe.txt`, `pf-liveness-detect.txt` V3b (the fail-open it already had, and the fix); `pf_no_state.sh:105-120` (`rulestat`, the counter read); `pf-grant-matrix.txt` G2/G3 (what the grant permits and refuses).

### DF193 — a guest can pre-create the on-create-done marker, and the host promotes it to permanent state on the next start, so setup commands never run

- **Discovered:** 2026-08-11, from the owner asking what a restart re-reads that an agent could have edited first · **Workstream:** isolation / lifecycle
- **Severity:** MEDIUM, and **user-dependent by construction.** On-create commands are user-configured, so the impact is whatever the user put in them. Suppressing a `npm ci` is a nuisance; suppressing a command that installs a wrapper, drops a privilege, or configures a proxy is a security control the agent switched off about itself. yoloAI cannot know which it is, which is the argument for not letting the guest decide.
- **Disposition:** PARKED — filed, not fixed. The channel is inherent (the guest is what runs the commands, so the guest is what knows they finished); what to do about it is a design choice between a start-scoped nonce and host-side observation of the result. Both are described below, neither is chosen.
- **Rides:** **any.** It withdraws nothing user-visible.
- **What is wrong.** `store.CreateDoneMarkerPath` resolves to `ReadWriteTierDir(sandboxDir)/lifecycle-on-create-done` (`internal/config/sandbox_layout.go:276`) — the **guest-writable** tier, by design, because `runtime/monitor/setup_helpers.py:75` writes it from inside the guest after on-create succeeds. On the next start, `syncLifecycleMarker` (`internal/orchestrator/lifecycle/lifecycle.go:82-93`) stats that path and, if present, sets `OnCreateCommandsDone = true` in `sandbox-state.json` — which lives in the **host** tier and is thereafter trusted. A `touch` inside the sandbox, at any time, is sufficient. It needs no root: the file is in the agent's own writable share.
- **Both directions are available.** Creating it early suppresses on-create commands on every subsequent start. Deleting it forces them to re-run, which is a cheaper lever than it looks if any of them are expensive or non-idempotent.
- **This is the third of its shape, and the first the tiering does not fix.** [DF136](findings-resolved.md) and [DF148](findings-resolved.md) are the same class — *a host action driven by a guest-writable file* — and both were closed by moving the file to a tier the guest cannot write. **That remedy is unavailable here**: the guest legitimately needs write access, so the fix has to change what the host *believes*, not where the file *sits*. Per GEN §18, three of a kind says the architecture generates this class, and the tiering closed exactly the subset where guest write access was accidental. The residue — files the guest must write and the host must read — has no owner and no rule.
- **Two candidate fixes, neither chosen.** (1) **A start-scoped nonce**: the host generates a value per start, passes it in, and ignores a marker that does not carry the current one. A root guest can still forge it *during* a start it is part of, but cannot pre-declare success for a start that never happened, which kills the cheap attack. (2) **Host-side observation**: the host learns the exit status of the on-create commands through a channel it owns rather than reading a file the guest wrote. Strictly better and strictly more work. Note that (1) degrades gracefully and (2) does not exist yet.
- **The general rule it argues for is DF192's (directly above), one layer out.** There, a *detector* sat on the wrong side of the trust boundary; here, a *lifecycle fact* does. The common form: **when the guest is the only party that can observe something, the host must treat its report as a claim, not as state** — and in particular must not copy it into host-tier storage where its origin is no longer visible. `sandbox-state.json` records `on_create_done` with nothing recording that a guest said so.
- **Not established:** whether any other host-read file lives in the read-write tier. `AgentStatusFileName` and `AgentRuntimeDirName` are both `ReadWriteTierDir` children (`sandbox_layout.go:204,209`) and were not traced for this finding. That sweep is the actual scope of the question the owner asked, and this entry is one instance of it.
- **Pointer:** `internal/config/sandbox_layout.go:276` (`CreateDoneMarkerPath`), `:204,209` (the untraced siblings); `internal/orchestrator/lifecycle/lifecycle.go:82-93` (`syncLifecycleMarker`); `internal/orchestrator/create/create.go:532` (`loadOnCreateDone`); `runtime/monitor/setup_helpers.py:75` (the guest writer).

### DF194 — a guest holding `CAP_NET_ADMIN` can unbind its own host-side enforcement by destroying its own interface, and the sandbox returns unenforced unless something reinstalls

- **Discovered:** 2026-08-12, verification round 2 item V4 · **Workstream:** isolation / Linux host-side enforcement
- **Severity:** LOW **as an escape** and **MEDIUM as a restart hazard**, and the split is the whole finding. Destroying the interface costs the guest its own network in the same instant, so on its own it is denial of service against itself rather than an exfiltration path. What makes it worth filing is the *next* start.
- **Disposition:** MITIGATED BY DESIGN, not fixed — part 0 of [`enforcement-build.md`](plans/enforcement-build.md) reinstalls enforcement before the agent runs, and that is now load-bearing rather than defensive. No separate release entry: it rides the brief that mitigates it.
- **Rides:** **any.** Nothing user-visible changes; a reinstall that already had to exist acquires a second reason.
- **What was measured.** A guest with `CAP_NET_ADMIN` was run against a netdev ingress chain bound to its host-side veth and told to defeat it five ways: add a second address, change its MAC, flap the interface down and up, rename its own end, and fragment its traffic. **It stayed blocked through all five**, each with a positive control proving the path still worked. Then `ip link del eth0` — a veth pair dies together, so the host-side device went with it, and the chain was left stale-but-inert.
- **Why it is not merely self-harm.** V5 established the chain binds by **ifindex**, not by name. So when the sandbox is restarted and the runtime builds a fresh veth, that veth carries a **new index** and the surviving chain will not follow it. The guest therefore does not have to win at the moment of the attack; it has to survive until the next start, at which point it is unenforced by a mechanism that looks, to rule inspection, exactly like a sandbox that never had a policy. The table still lists as present (V1).
- **What makes it tractable.** The same event is loud on the link group: `RTNLGRP_LINK` announces the device's disappearance and **names the veth** (V1b), including in this hostile case specifically, with the other sandbox's veth untouched in the same window. So the host can see it happen. Detection is not the gap; reinstallation is.
- **The generalisable half**, which is why this is filed rather than only noted: **a key that is immune to inheritance is, by the same property, immune to re-attachment.** Binding to a device instance is what makes a returning sandbox unable to inherit a departed policy — and what makes it unable to inherit its *own*. Any future key chosen for non-recycling gets this the same way, and the reinstall it implies should be designed in rather than discovered.
- **Not established:** whether any backend restores a destroyed interface *without* going through yoloAI's start path, which is the case that would turn this into a live escape rather than a restart hazard. Nothing tests rootless podman or containerd here, and nothing measures whether a guest can time the destruction to race a reinstall.
- **Pointer:** `design/research/linux-enforcement/results/v4-hostile-guest-vs-netdev.txt` (the five attacks and the teardown), `v2-v5-netdev-device-binding.txt` (the ifindex binding), `v1b-link-event-coverage.txt` (the link event, hostile arm), `design/plans/enforcement-build.md` § *Part 0*.

### DF195 — `--env` comma-splits its value on `new`/`run` but not on `start`/`restart`/`reset`, so an ordinary value cannot be passed on the path that creates the sandbox

- **Discovered:** 2026-08-12, building the P2 chokepoint harness · **Workstream:** CLI
- **Severity:** LOW–MEDIUM (a shipped flag rejects ordinary input on two commands and accepts it on three, and the error blames the user's value)
- **Disposition:** UNRESOLVED — found while doing something else, recorded rather than fixed mid-round
- **Rides:** **any** for the fix itself. Arguably **breaking** in one direction: anyone relying on `--env A=1,B=2` to set *two* variables in one flag would lose that, and it works today by accident.
- **Description:** `internal/cli/lifecycle/new.go:66` declares `--env` as `StringSlice`, which splits every value on commas. So `--env NO_PROXY=localhost,127.0.0.1` is parsed as two values, the second has no `=`, and the command exits 2 with `invalid --env value "127.0.0.1": must be KEY=VAL` — an error naming a fragment the user never wrote as a value. Commas are ordinary in environment values: `NO_PROXY`, `JAVA_TOOL_OPTIONS`, `GOFLAGS`, any comma-separated list.
- **Why it is a defect rather than a preference: three sibling paths already do it the other way.** `restart.go:42`, `start.go:41` and `reset.go:46` all declare the *same* `--env` flag as `StringArrayVar`, which does not split. So `--env NO_PROXY=localhost,127.0.0.1` is rejected by `yoloai new` and accepted by `yoloai restart` — the same spelling, the same flag name, opposite behaviour, decided by which command you reached it through. The fix direction is therefore to make `new`/`run` match the three that are already right, not to invent a mechanism ([GEN §18](../principles/general-principles.md)).
- **The shape, checked rather than assumed.** `new.go` has three other `StringSlice` flags and they are not the same case: `--network-allow` takes domains, `--port` takes `host:container`, and neither can contain a comma, so splitting is correct there and is arguably the point. `--dir` is the one other value that is a filesystem path and could in principle contain a comma; it is far rarer and is not separately filed. `--runtime` is already `StringArray`. So this is one flag with the wrong type, not a class.
- **What would close it:** `StringSlice` → `StringArray` for `--env` on `new`/`run`, plus a test that a value containing a comma survives to the sandbox as one variable. Rule 10's red-on-revert is straightforward here. Decide at the same time whether the lost split is worth a `BREAKING-CHANGES.md` entry — it is a withdrawal of behaviour that works today, even though nothing documents it.
- **Pointer:** `internal/cli/lifecycle/new.go:66` and `:219`, against `internal/cli/lifecycle/restart.go:42`, `start.go:41`, `reset.go:46`.

### DF196 — `--network-none` silently swallows an allowlist: `--network-allow` is accepted, discarded, and never recorded

- **Discovered:** 2026-08-12, checking the loud-failure requirement for the network-mode reshape · **Workstream:** isolation
- **Severity:** MEDIUM (a user asks for network access, is told nothing, and gets a sandbox with none — the request is not refused, not warned about, and not stored)
- **Disposition:** UNRESOLVED — found while scoping [network-mode-reshape.md](plans/network-mode-reshape.md), which carries the fix
- **Rides:** **breaking.** The fix is newly-rejected input on a combination that is accepted today (rule 1).
- **Description:** `yoloai run box dir -p … --network-none --network-allow example.com` **exits 0** and creates a running sandbox. The stored `netpolicy.json` is `{"version": 1, "network_mode": "none"}` — no `allow` key at all — and the guest has only `lo`. The user asked for a destination, was not refused, was not warned, and the request left no trace anywhere for a later reader to notice.
- **Where it happens.** `netpolicy.Compose` (`internal/netpolicy/compose.go:58`) is `case "none": return "none", nil` — it discards **both** the agent floor and the user list without inspecting them. The CLI does not catch it earlier: `--network-none` and `--network-isolated` are mutually exclusive (`new.go:74`), but `--network-allow` only *implies* isolation, and that implication does not participate in the exclusion, so the pair passes validation.
- **Why the obvious diagnosis is wrong, and the fix belongs one layer down.** Making the CLI reject the flag pair would fix the CLI and leave the **library** open, which is the door that matters most: `Client.CreateSandbox` → `SandboxCreateOptions.toInternal()` → `Engine.Create` never passes through `internal/cli` at all, and `toInternal` is a pure field copy with no validation anywhere after it. An integrator passing `Network: NetworkModeNone` with `NetworkAllow` set gets the same silent discard, and nothing in the public surface says otherwise. A **profile** is a third door — narrower than an earlier draft of this entry claimed, since `config.NetworkConfig` is `Isolated bool` + `Allow []string` with no mode key, so it can supply the allowlist half but never `none`.
- **`Compose` is the right place for *this* half and cannot be the whole answer.** It has exactly one call site (`internal/orchestrator/create/prepare_dirs.go:342`), downstream of all three doors, so the allowlist check belongs there. But `Compose` sees only the mode and two domain lists — it cannot see the requested **ports**, the chosen **agent**, or the broker setting, each of which is the same question asked about a different field. See DF197: the two together are symptoms of a missing single validation of *what the requested mode can honour*, run once after resolution when the resolved mode and the fully-merged request are both in hand.
- **The sibling path is already correct, which is what makes this a defect rather than a design choice.** At *runtime* the same request fails loudly: `Network.Allow` → `requireIsolated` returns `sandbox %q uses --network-none; cannot modify network access` (`network.go:242`). So the product already holds the position that an allowlist under `none` is a usage error; creation is the one entry point that does not, and it is the one where the user is most likely to try.
- **What would close it:** `Compose` returns an error when `mode == "none"` and either list is non-empty, with a message naming the mode and the domains. Rule 10's red-on-revert is easy — `compose_test.go` already exercises the `"none"` case and asserts the silent discard, so the test that pins the current behaviour is the test to invert. Decide at the same time whether an **empty** user list plus a non-empty **agent floor** is also an error: it is reachable with `--agent claude --network-none`, and refusing it would make `none` unusable with any real agent, which per [P9](research/proxy-chokepoint/results/p9-network-none-utility.txt) is already true in practice but is not currently *said*.
- **Pointer:** `internal/netpolicy/compose.go:57-63`, `internal/netpolicy/compose_test.go:52`, `internal/cli/lifecycle/new.go:74` and `:191`, `profile_config.go:60`, against the correct `network.go:242`.

### DF197 — `--port` is refused with `--network-none` at the CLI only, so a profile's or archetype's ports are accepted and silently dropped

- **Discovered:** 2026-08-13, auditing [network-mode-reshape.md](plans/network-mode-reshape.md) · **Workstream:** CLI / isolation
- **Severity:** LOW–MEDIUM (same shape as DF196, one flag over: a request is accepted, discarded, and left unrecorded)
- **Disposition:** UNRESOLVED — the reshape plan carries the fix as step 1, alongside DF196
- **Rides:** **breaking.** Refusing a profile+mode combination that is accepted today is newly-rejected input.
- **Description:** `internal/cli/lifecycle/new.go:207` refuses `--port` with `--network-none` by reading `cmd.Flags().GetStringSlice("port")` — **the flag only**. Ports also arrive from a profile (`internal/orchestrator/create/prepare_profile.go:141`, `:199`, which *prepend* to `opts.Ports`) and from devcontainer archetypes (`prepare_archetype.go:272`). Neither path passes the check, and the library API validates nothing (`sandbox_options.go:81`). So a profile carrying `ports:` plus `--network-none` creates a sandbox whose ports can never work, with no error and nothing recorded.
- **This is the second instance of one defect class, which is the part worth acting on** ([GEN §18](../principles/general-principles.md)). DF196 is the same failure for the allowlist: a CLI-level guard over a value that three doors can set. Two of a kind on adjacent flags says the architecture invites it — the guards are written where the *flag* is parsed rather than where the *value* is resolved. The fix for both is one layer down, at the point the mode and the request are finally composed, and doing them separately would be two mechanisms for one job.
- **The sibling path that is already right:** the runtime allowlist verb. `Network.Allow` → `requireIsolated` (`network.go:243`) refuses on a `none` sandbox regardless of how the request arrived, because it validates against the *stored* mode rather than against the flag that produced it.
- **The library is a door too, and it is the one with no guard at all.** `Client.CreateSandbox` → `toInternal()` → `Engine.Create` bypasses `internal/cli` entirely; `toInternal` copies `Ports` and `Network` across verbatim (`sandbox_options.go:165-167`) and nothing validates them afterwards. So an integrator asking for `NetworkModeNone` with ports gets a sandbox whose ports can never work, with no error — the CLI check is not merely incomplete, it is absent from the path most likely to be automated.
- **What would close it, and it is shared with DF196.** Neither is really "a guard in the wrong place"; together they are **a missing validation step**. The resolved mode and the fully-merged request only coexist at one point in `create.Create`: after Phase 1 has merged profile and archetype ports into `opts.Ports` (`prepare_profile.go:141`, `:199`, `prepare_archetype.go:283`) and after Phase 3's `buildConfigAndEnvironment` has resolved the mode. One function there — *does this configuration fit this mode?* — covers ports, the allowlist, the agent and the broker in one pass, from every door. Writing three more field-specific guards would be the fourth mechanism for one job (GEN §18). Test the **library** door specifically; the flag door already has one (`new_test.go:67`) and is the door that was never broken.
- **Pointer:** `internal/cli/lifecycle/new.go:207-208`, `internal/orchestrator/create/prepare_profile.go:141` and `:199`, `internal/orchestrator/create/prepare_archetype.go:272`, `sandbox_options.go:81`, against `network.go:243`.

- **Discovered:** 2026-08-13, auditing [network-mode-reshape.md](plans/network-mode-reshape.md) · **Workstream:** isolation
- **Severity:** **HIGH** (a user-facing security claim that is false on half the backends, for the mode the product recommends when the allowlist cannot be trusted)
- **Disposition:** UNRESOLVED — **the apple and tart halves are now measured on hardware and confirmed** ([`c3-network-none.txt`](research/mac-channel/results/c3-network-none.txt), 2026-08-13, harness v2, through yoloAI's own launch path per A37). containerd remains a static reading, verifiable on the Linux dev host.

The IPv6 half is worth stating separately: even a correct v4 fix would leave a reachable global v6 address on apple, which is DF179's family gap arriving by a second route.

  - **containerd** — `runtime/containerd/lifecycle.go:527` says so in its own comment: *"the `runtime.NetworkMode == "none"` CLI flag is not currently honored by the containerd backend (setupCNI is unconditional)"*. `cfg.NetworkMode` has no other consumer in that package.

This is the same class as the correction made 2026-08-12 to the docker allowlist claim: each mechanism statement was written accurately and the *conjunction* was never checked against the backends.

- **The remedy for apple is one flag, and it is measured.** `container run --network none` yields a guest with only `lo` and no egress, and `none` is a *special* value rather than an unattachable name — a bogus network name errors (`network bogusnet123 not found`) while `none` succeeds. So the apple fix is passing the flag, not building a mechanism. For tart the analogous surface is `--net-softnet-block=0.0.0.0/0` (C2), which `runtime/tart` also does not pass.
- **The conformance case that should have caught this cannot fail, independently of which backends run it.** `runtime/runtimetest/conformance.go:165` wraps its only assertion in `if err == nil`, so an `Exec` that errors for *any* reason passes the case unconditionally — a probe with no negative self-test, the class [D136](../decisions/working-notes.md) §3 exists to stop. That is a second defect on top of the suite-membership one already noted above: fixing which backends run it would still not make it discriminate. Filed as [DF200](#df200--the-networknone-conformance-case-cannot-fail-and-does-not-run-on-any-backend-that-has-the-defect).

- **Severity:** **MEDIUM** (the mode is unusable on one backend, and fails in a way that names nothing a user could act on)

- **Description:** `internal/config/host_env.go:157-158` deliberately limits config/profile `${VAR}` interpolation to `HOME`, `USER`, `LANG`, `TZ` and the `LC_` prefix — the comment at `:155` says this is what closes arbitrary config interpolation. But `internal/agent/fileagent.go:84,88` lets a YAML file under `~/.yoloai/agents/` declare `api_key_env_vars` and `auth_hint_env_vars`, which reach `HostEnv.EnvForAgentCredentials` (`host_env.go:285`) and are read **from yoloAI's own process environment** and delivered into the sandbox as secrets. So a config file can name `AWS_SECRET_ACCESS_KEY` or `GITHUB_TOKEN` and have it injected — the same capability `${VAR}` was locked down to prevent, reached by another name.
- **The entire security argument is one `//nolint` comment nobody sees.** `fileagent.go:237` reads the agent YAML with `//nolint:gosec // G304: f is a glob match under AgentsDir(), a trusted data dir (DataDir/agents/)` — that "trusted data dir" assertion is the whole basis for treating declared env-var names as safe to read and forward, and it is stated nowhere a user would encounter it.
- **Shipped agents already reach wide, which is the existing baseline this defect extends.** `agent.go:503` declares `opencode`'s `AuthHintEnvVars` as `GITHUB_TOKEN`, `AWS_ACCESS_KEY_ID`, `AWS_PROFILE`, `AZURE_OPENAI_ENDPOINT`, among others — the mechanism already forwards broad ambient credentials for a built-in agent; a file-defined agent can name anything at all.
- **The principle this violates:** ambient config must not be able to leak in via a config file — the CLI (an explicit flag, an explicit `--env`) is the legitimate channel for that. `${VAR}` interpolation was narrowed for exactly this reason, and a sibling mechanism reopens it under a different name.
- **Pointer:** `internal/config/host_env.go:155-158,285`; `internal/agent/fileagent.go:84,88,237`; `internal/agent/agent.go:503`.

### DF206 — config and profile `network.allow` entries are silently discarded whenever the mode is set explicitly

- **Discovered:** 2026-08-13, during the config-key trust audit · **Workstream:** config/trust seams
- **Severity:** MEDIUM (the discarded list is the egress allowlist)
- **Disposition:** UNRESOLVED — PARKED
- **Rides:** **any**.
- **Description:** `internal/orchestrator/create/prepare_profile.go:144` and `:208` gate the entire network block on `opts.Network == NetworkModeDefault`. So any explicitly-set mode makes the block skip, discarding every config- and profile-level `network.allow` entry without a word — **including when the mode was set implicitly by `--network-allow` itself**, which promotes `networkIsolated` to true at `internal/cli/lifecycle/new.go:197-199` before `prepare_profile.go` ever runs. `docs/GUIDE.md:679` documents this key as "additive with agent defaults", with no mention of this silent-discard condition.

- **Severity is MEDIUM rather than LOW** because the discarded list is the egress allowlist: the user believes a destination is permitted and it is not, or believes their config narrowed something when it was silently dropped.
- **Pointer:** `internal/orchestrator/create/prepare_profile.go:144,208`; `internal/cli/lifecycle/new.go:197-199`; `docs/GUIDE.md:679`; against [DF196](#df196----network-none-silently-swallows-an-allowlist---network-allow-is-accepted-discarded-and-never-recorded), [DF197](#df197----port-is-refused-with---network-none-at-the-cli-only-so-a-profiles-or-archetypes-ports-are-accepted-and-silently-dropped).
