== I1 HELD vs RELEASED — is an index ever handed out while a sandbox still holds it? ==
        K4c deleted the network before recreating it, so it measured recycling AFTER RELEASE. That is
        not the question a claim-time check turns on. Here four networks are created and HELD (each
        with a container attached, since N1b found the bridge exists only while something is), and
        then new networks are created against them.
        held: yb-i-a / ybi1 -> bridge101
        held: yb-i-b / ybi2 -> bridge102
        held: yb-i-c / ybi3 -> bridge103
        held: yb-i-d / ybi4 -> bridge104
        distinct bridges among the four held: 4 of 4
   PASS    I1a: four concurrently-held networks hold four distinct bridge indices
        
        I1b  now create two MORE networks while all four are still held. If either is handed an index
             that a live sandbox is using, interface keying is defeasible by an unrelated start.
        new while four held: yb-i-e -> bridge105   yb-i-f -> bridge106
        collisions against a held index: 0
   PASS    I1b: NO held index was reassigned. Recycling happens on release, not under a live holder.
        
        I1c  THE CONTROL. A negative in I1b is only meaningful if this allocator recycles at all — if
             it never reuses an index, I1b passed for free. Release two and create one.
        released: yb-i-c (was bridge103), yb-i-d (was bridge104), yb-i-f (was bridge106)
        next network created got: bridge103   (released set: bridge103 bridge104 bridge106)
   PASS    I1c: a RELEASED index was reused — the allocator does recycle, so I1b's negative is real

== I2 THE DETACH WINDOW — a sandbox that restarts releases its index without releasing itself ==
        N1b: a network has no host bridge until a container attaches, and the bridge goes away on
        detach. So an ordinary sandbox restart opens a window in which the index is free while the
        sandbox still exists and its pf rule still names it. If another sandbox can take it there,
        a claim-time read is NOT sufficient and interface keying fails on macOS for a reason that has
        nothing to do with K4c.
        sandbox A = ybi1 on yb-i-a, currently bridge101
        A stopped. its bridge now: <gone, as N1b predicts>
        creating a NEW sandbox inside A's detach window:
        the sandbox started during the window got: bridge101
        A restarted and came back on: bridge101  (it was bridge101)
        the window sandbox is NOW on: <no bridge>  (it was bridge101 when it started)
          => its index CHANGED while it was running and untouched. Whatever a rule named for it at
             claim time no longer refers to it, without that sandbox doing anything at all.
          egress with NO policy loaded: window sandbox->1.1.1.1=000   A->1.1.1.1=301
   FAIL    I2c: A RUNNING SANDBOX LOST ITS EGRESS because an unrelated sandbox restarted. It is still
             'running', it never asked for anything, and no policy is loaded. That is a backend
             defect in its own right, separate from every keying question on this page.
        
        the state both readings came from, verbatim:
          ybi1: state=running addr=192.168.65.3 gw=192.168.65.1
          ybi5: state=running addr=192.168.68.2 gw=192.168.68.1
          host bridges and their addresses:
             127.0.0.1
            bridge0 192.168.0.157
            bridge0 100.107.208.103
            bridge100 192.168.139.3
            bridge102 192.168.66.1
            bridge103 192.168.67.1
            bridge101 192.168.65.1
          the two gateways differ (192.168.65.1 vs 192.168.68.1), so the shared bridge NAME above is an index
          reuse and not a subnet collision — the addresses stayed distinct.
   FAIL    I2: THE WINDOW IS REAL — a new sandbox took A's index while A was merely restarting.
            A rule naming bridge101 now governs a different sandbox, and A never released its network.

== I3 THE INGRESS TAG, PER SANDBOX — K3's one positive result, re-asked on per-sandbox networks ==
        K3 established that a tag applied on INGRESS, keyed on the bridge and on no address, survives
        NAT and is matchable on the egress rule. It was applied on the shared default bridge, so it
        tagged every guest identically and could not be a per-sandbox key. With one network per
        sandbox each guest arrives on its own bridge, which is what would make the tag discriminate.
        A=ybi1 on bridge101   B=ybi2 on bridge102   egress=en0
        rules loaded: 3   (no address appears in any of them)
        A->1.0.0.1 =000   (000 => A's own tag reached the egress rule)
        B->1.0.0.1 =301   (non-000 => B was NOT caught by A's rule — this is the discrimination)
        A->1.1.1.1=301  (non-000 => the tag did not blanket-block A — control)
        host->1.0.0.1=301 (non-000 => untagged host traffic untouched — control)
   PASS    I3: THE INGRESS TAG IS PER-SANDBOX. Two guests, one blocked and one not, under a ruleset
            containing no address at all — the same shape Linux's K1 established there.

== I4 DOES A RULE SURVIVE ITS INTERFACE DISAPPEARING? — this decides what I2 costs ==
        I2 showed the index is released whenever a sandbox detaches. What that COSTS depends entirely
        on something nobody has measured: whether a loaded rule naming `bridgeN` re-attaches when a
        bridge of that name comes back, or silently matches nothing from then on.
          re-attaches  -> the exposure is the restart window, and a claim-time read plus teardown is
                          close to sufficient.
          goes inert   -> EVERY sandbox is unenforced after its first restart, with pf reporting a
                          correct-looking ruleset throughout. That is the shadowed-anchor failure
                          again, one level down, and it would not be visible to any rule inspection.
        
        I4a  will pf even accept a rule naming an interface that does not exist? (pre-loading a pool
             of per-sandbox rules at install time depends on it)
        loading a rule on bridge999 -> rc=0 <no output>
   PASS    I4a: pf accepts a rule naming an absent interface (it resolves by name, not at load time)
        
        I4b  THE DECIDING ARM. A is enforced by an interface-keyed rule with no source address in it.
             Nothing else is started, so the index is not raced — this is an ordinary restart alone.
        before restart: A on bridge101  ->1.1.1.1=301  ->1.0.0.1=000  (need non-000 then 000)
   PASS    I4b precondition: the interface-keyed rule enforces, with no source address in it
        A stopped. bridge carrying its gateway now: 
        the anchor's rules while the interface is GONE (pf keeps them, which is the trap):
          pass in quick on bridge101 inet proto tcp from any to 1.1.1.1 flags S/SA keep state
          block drop in quick on bridge101 proto tcp all
        A restarted: bridge=bridge101 (was bridge101), address=192.168.65.4
        NOTHING has been reloaded. Asking the same two questions again:
        after restart:  ->1.1.1.1=301  ->1.0.0.1=000
   PASS    I4b: the rule RE-ATTACHED. Same index, no reload, and the denied destination is still
             blocked while the allowed one still reaches — and A's address changed to 192.168.65.4,
             which the rule never named. pf resolves the interface by name at match time, so
             I2's window is a window and not a permanent lapse.

== VERDICT — composed from the values above, not asserted ==
        held index reassigned while live : yes
        allocator recycles at all        : yes
        restart/detach window            : hazard
        ingress tag per sandbox          : per_sandbox
        rule survives its interface going away: yes
        
   FAIL    macOS HAS the key, and ONE lifecycle rule is the whole price. Everything the key needs works:
            a held index is never reassigned, the interface discriminates with no address in the
            rule, the ingress tag is per-sandbox, and a rule re-attaches BY NAME when its interface
            comes back — A's address changed underneath it and enforcement did not lapse.
        
            The single failure is the detach window. A sandbox that merely restarts gives up its
            index, and a sandbox started in that window can take it — at which point the stale rule
            governs a STRANGER, which is worse than not enforcing. So the key is usable if and only
            if rule maintenance is bound to attach and detach: withdraw the rule when the interface
            goes, re-read the real index and re-establish it when the interface returns.
        
            That is a lifecycle requirement, not a missing key, and it is a far smaller gap than
            'there is no stable per-sandbox non-address key', which is what closed this on macOS.
            The platforms are closer than the divergence suggested: Linux needs no such rule because
            its names do not recycle, macOS needs one because its indices do.

== WHAT WAS NOT TRIED ==
        - tart. Its guests share the vmnet bridges rather than getting one network each, so none of
          I1-I3 transfers to it; the question there is a different one and it is not asked here.
        - Concurrent starts. The detach window in I2 is opened by hand, one sandbox at a time. Two
          sandboxes racing for a freed index is the case a real pool would hit and it is not run.
        - Whether the re-attach in I4 holds when a DIFFERENT sandbox takes the name. I4 restarts A
          alone and A gets its own index back, so the rule re-attaches to the same sandbox. The
          hazard I2 describes is the other case, and combining them -- stale rule, name reused by a
          stranger -- is the experiment that would price the window rather than just naming it.
        - The tag namespace. Whether pf tags are a limited resource, and what happens at 32 of them,
          is unmeasured; K3 and I3 both use two.
        - Any of this under the shipped D132 grant. Every rule here is loaded as root. The grant
          authorizes table membership, and an interface-keyed or tag-keyed design needs RULES to
          change per sandbox, which the grant does not permit at all. That is the largest untested
          consequence of a positive result here, and it is a D132 question rather than a pf one.
