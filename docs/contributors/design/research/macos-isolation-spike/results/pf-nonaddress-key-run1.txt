== K1 PROCESS IDENTITY — is guest traffic attributed to any uid/gid? ==
        pf matches `user`/`group` against the socket that owns a packet. A VM's packets are
        forwarded, not generated locally, so they should own no socket — but that is the assumption
        under test. `user unknown` matches exactly the no-socket case, so the two rules split it.
        
        K1a  rule: block in quick on bridge101 proto tcp from any to 1.0.0.1 user unknown
        guest->1.0.0.1=000000   host->1.0.0.1=301  (host is the control: it owns a socket, must stay non-000)
   FAIL    K1a: guest was NOT matched by `user unknown` — it does own a socket. Investigate.
        
        K1b  rule: block in quick on bridge101 proto tcp from any to 1.0.0.1 user = 501
             If the VM's traffic were attributed to the user running it, this would block the guest.
        guest->1.0.0.1=301   (non-000 => not attributed to uid 501)
             control: the same rule shape on the OUTBOUND path must bite the HOST, or K1b proves nothing
        host->1.0.0.1=000000   (000 => the rule form works and pf does match user for real sockets)
   UNKNOWN K1b: the control failed — the rule never bit the host, so the guest result means nothing

== K3 TAGS ACROSS NAT — does an ingress tag survive translation? ==
        The tag is assigned by a rule keyed on the BRIDGE, never on an address, so this is a genuine
        non-address key if it holds. What makes it valuable: after NAT every guest wears the host's
        address, so nothing else can tell guest traffic from host traffic on the way out.

        K4c  DOES THE BRIDGE INDEX RECYCLE? This is the whole question. An address recycles, which
             is why rules 1/1b/1c exist. A key that recycles the same way is the same hazard with a
             new name, and a stale rule naming bridge103 would silently apply to whoever gets it next.
        after deleting yb-k-b: bridge103 is gone

             the result this item existed to get.

== WHAT WAS NOT TRIED — so the negative is readable as the bounded claim it is ==
        - tart. Its guests use the same vmnet bridges, so K1/K2/K3 should transfer, but only the
          apple backend was measured here. `--net-softnet` is a separate mechanism (it filters in
          a helper process, not pf) and was not examined.
        - The vmnet network ceiling. How many networks can exist at once, and whether creation
          fails or degrades at the limit, decides whether one-network-per-sandbox is even feasible.
        - pf `label`, `probability`, `os` fingerprinting, `rtable`. Labels name a rule, not a
          packet; the others are not identity.
        - NetworkExtension flow attribution, which CAN see the owning process — but only for host
          processes, and it does not see forwarded VM traffic. That is M6.
        - Whether the guest can be made to SET something matchable (a DSCP/TOS bit, a source port
          range). It can, which is exactly why it is not a security key: the guest controls it.
