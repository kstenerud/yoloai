            THAT IS THE PROBLEM, not the reassurance it looks like. The rewritten plan keys
            enforcement on the host-side interface; those rules name a bridge whose index is assigned
            dynamically and changes across a restart. Under D132 as written, the unprivileged side
            cannot write them, and the pinned file cannot contain them because nobody knows the
            indices at install time. So interface keying needs EITHER a privileged component that
            authors rules at claim time, OR a pinned superset naming every index the host could ever
            hand out, OR a wider grant. The plan picks none of these because it has not noticed.

== G5 THE ESCAPE — a pinned SUPERSET with tables keyed by bridge INDEX ==
        G4 says interface keying does not fit the grant. That is only worth reporting alongside what
        would fit, and two candidates exist.
        
        The clean one is pf interface GROUPS: bind bridge101 into a group with ifconfig and let a static
        rule say `on <group>`. macOS does not have them. Measured, not assumed:
          ifconfig lo0 group ytest_probe -> ifconfig: group: bad value
          man ifconfig mentions 'group': 0 time(s)
          Closed, and it was the best idea.
        
        The surviving one inverts the pool. Instead of a slot per sandbox whose rule names that
        sandbox's interface, have a slot per BRIDGE INDEX: the pinned file enumerates every index the
        host could hand out, each with its own table, and claiming a sandbox means adding its allowlist
        to the table named after the index it landed on. Rules stay static, the unprivileged side still
        only ever changes table membership, and the key is still the interface. The grant's regex would
        need to cover the index range — a pattern change, not a model change.

== WHAT WAS NOT TRIED ==
        - What the superset costs at evaluation time. G5 loads 41 indices; a host could hand out
          more, and every packet is now evaluated against a first-match list dominated by rules for
          interfaces that do not exist. pf-no-state.txt already declines to price per-packet
          evaluation, and this makes that gap bigger rather than smaller.
        - What happens when a sandbox lands on an index OUTSIDE the superset range. It would meet no
          rule at all and be silently unenforced — fail-open, the worst direction. That needs a
          preflight assertion nobody has written.
        - Whether a privileged claim-time component is acceptable at all. That is a product decision
          about what may run as root, not a measurement, and it is the likeliest real answer.
        - sudo's regex matching itself. The grant is taken verbatim from the plan and validated, but
          no attempt was made to defeat the regexes -- argument smuggling, alternate pfctl paths,
          symlinks, or `--` handling. A permit/refuse matrix is not a review of the pattern.
        - Any form of the grant other than the one the plan states. If the plan's text is wrong, this
          measures the wrong boundary faithfully.
        - The lifecycle rule's reload CADENCE against sudo. Every reload is a sudo invocation and
          pf-pool-scaling.txt priced one at ~7.9 ms; nothing here multiplies that by a detach/return
          rate, and pf-lifecycle.txt's daemon reloads on every transition.
