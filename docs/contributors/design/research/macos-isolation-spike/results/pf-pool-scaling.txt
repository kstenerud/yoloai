== P2 IS IT LINEAR? — the question the 'shrink the pool' lever depends on ==
        If cost = a + b*(N+3), then a and b fall straight out of two points and the third checks it.
        fitted from n=8 and n=32:
          per-call cost b   =  18.81 ms
          fixed overhead a  =   10.2 ms
        check against the measured n=16 point:
          predicted 367.6 ms, measured 367.6 ms, error 0.0 ms (0.0%)
        => LINEAR within 10%. Cost is dominated by the per-call term, so pool size is a
           real latency lever: halving the pool removes (N/2) sudo invocations.

        What each size costs a sandbox start, using the fit:
           4 slots ->  141.9 ms
           8 slots ->  217.1 ms
          16 slots ->  367.6 ms
          32 slots ->  668.5 ms

== P3 THE DENOMINATOR — what a sandbox start costs without any of this ==
        A latency lever is only worth pulling against the thing it is a fraction of. This measures
        `container run -d` — the backend's own create — which is the floor. A full `yoloai new` is
        larger (~2.4s in earlier runs), so the percentages below are the PESSIMISTIC framing: against
        a real sandbox start, acquisition is a smaller fraction than this section makes it look.
        start 1: 715 ms
        start 2: 679 ms
        start 3: 633 ms
        mean start: 676 ms
        acquisition at 32 slots is 98.9% of that;
        at 8 slots it is 32.1%.

== P4 WHAT THE POOL SIZE ALSO BUYS — the axis that is not latency ==
        Slots are the concurrency ceiling: N slots means at most N isolated sandboxes at once, and
        the (N+1)th either waits or runs unenforced. Neither is measured here — the exhaustion policy
        is a design decision, not a measurement — but the trade is not latency-versus-nothing.
        pf's own limits, for the record:
          states        hard limit    10000
          app-states    hard limit    10000
          src-nodes     hard limit    10000
          frags         hard limit     5000
          tables        hard limit     1000
          table-entries hard limit   200000

== WHAT WAS NOT TRIED ==
        - Sizes above 32. The shipped grant's regex tops out at slot 31, so a larger pool is a
          grant change and not just a parameter.
        - Concurrent acquisitions. Every measurement here is one acquisition at a time on an idle
          host. Two sandboxes starting together contend for the same pfctl and the same sudo, and
          that is exactly the case the pool exists for.
        - Allowlist size. pf-acquire-cost.txt already measured that a call's cost does not scale
          with the number of addresses in it, which is why the adds are two calls and not forty.
        - The exhaustion policy. What the (N+1)th sandbox does is unmeasured and undecided.
