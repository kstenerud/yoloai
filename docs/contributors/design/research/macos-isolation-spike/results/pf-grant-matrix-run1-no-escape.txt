        This is the question the interface-keyed rewrite creates. Its rules say `on bridge101`, and
        bridge indices are dynamic, per-sandbox, and change across a restart; pf-lifecycle.txt then
        reloads the anchor on every detach and return with different interface names each time. D132's
        model has the unprivileged side changing table MEMBERSHIP only, never rule TEXT.

   PASS    G4: no interface-keyed rule could be installed by the unprivileged user through any route.
            THAT IS THE PROBLEM, not the reassurance it looks like. The rewritten plan keys
            enforcement on the host-side interface; those rules name a bridge whose index is assigned
            dynamically and changes across a restart. Under D132 as written, the unprivileged side
            cannot write them, and the pinned file cannot contain them because nobody knows the
            indices at install time. So interface keying needs EITHER a privileged component that
            authors rules at claim time, OR a pinned superset naming every index the host could ever
            hand out, OR a wider grant. The plan picks none of these because it has not noticed.

== WHAT WAS NOT TRIED ==
        - The superset idea. A pinned file naming bridge100..bridge13x for every slot would keep the
          grant intact and is the obvious escape, but nothing here writes one or checks whether pf
          accepts rules naming interfaces that do not exist yet at that scale. (pf-interface-key.txt
          I4a says it accepts them singly.)
        - Whether a privileged claim-time component is acceptable at all. That is a product decision
          about what may run as root, not a measurement, and it is the likeliest real answer.
        - sudo's regex matching itself. The grant is taken verbatim from the plan and validated, but
          no attempt was made to defeat the regexes -- argument smuggling, alternate pfctl paths,
          symlinks, or `--` handling. A permit/refuse matrix is not a review of the pattern.
        - Any form of the grant other than the one the plan states. If the plan's text is wrong, this
          measures the wrong boundary faithfully.
        - The lifecycle rule's reload CADENCE against sudo. Every reload is a sudo invocation and
          pf-pool-scaling.txt priced one at ~7.9 ms; nothing here multiplies that by a detach/return
          rate, and pf-lifecycle.txt's daemon reloads on every transition.
