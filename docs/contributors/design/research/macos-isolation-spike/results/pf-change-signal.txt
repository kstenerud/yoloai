== S3b THE ONE FIELD THAT MATTERS — does anything in the GRANTED read move? ==
        'pfctl -s info' is already permitted by the shipped D132 grant, so a field that changes on a
        ruleset load would give a poll that costs no new privilege at all. Counters that always move
        (searches/inserts) are useless — they change whether or not anything happened.
        uptime before a plain reload : 0 days 00:00:04  (4s)
        uptime after  a plain reload : 0 days 00:00:06  (6s)   a RELOAD is the dangerous quiet case
        uptime before -F all         : (6s)
        uptime after  -F all         : (0s)
        (a reset means the counter went BACKWARDS; 2s of elapsed time makes it go forwards)
        
        counter reset by a reload: no    by -F all: yes
   PASS    S3b: A PARTIAL SIGNAL EXISTS, AND IT IS FREE. `pfctl -s info` is already in the shipped
            grant, and its 'Enabled for' counter RESETS on `-F all` — so a poll that remembers the
            previous value detects a flush with no new privilege, by seeing the uptime go backwards.
            But it does NOT move on a plain reload, and a reload that omits the anchor line is
            exactly the fault that defeats every other check. So this is a cheap tripwire for the
            loud fault, not a detector for the quiet one — it cannot replace a behavioural probe.
        main-refs after repair = 2

== S4b THE FILE WATCH, REFUTED EXPLICITLY ==
        Watching /etc/pf.conf is the first idea anyone has. Above, every event left its mtime
        untouched — including the one that voided enforcement. The file is the SOURCE; the fault is in
        the LOADED ruleset, and nothing keeps the two in agreement. A file watcher is not a weak
        detector here, it is a blind one.

== S5 THE COST OF POLLING, since that is what a negative forces ==
        20 invocations of the granted read, as the user would issue them:
        pfctl -s info x20 (as root, no sudo): 2.0 ms each
        pfctl -s rules x20 (the main-ruleset read a poll would need): 4.3 ms each
        
        Add ~9.3 ms of sudo per call (pf-acquire-cost.txt, where 85% of a call was sudo and not pfctl).
        At a 5s interval that is a fraction of a percent of one core, and a 5s worst-case window of
        unenforced running. The interval is the design parameter; these are its two axes.
