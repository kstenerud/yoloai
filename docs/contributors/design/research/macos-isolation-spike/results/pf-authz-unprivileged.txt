macOS pf authorization — what can be settled WITHOUT root
=========================================================
Host: macOS 26.5.1 (Darwin 25.5.0), sudo 1.9.17p2, sudoers grammar 50, SIP enabled.
Date: 2026-08-03. Run by: unprivileged probing only (no sudo credential available).
Companion harness for the privileged half: ../pf_authz.sh (written, NOT yet run).

WHY: the design needs UNATTENDED privilege — `yoloai stop` and any reaper run with no
tty, so the teardown call cannot prompt. That forces a NOPASSWD sudoers grant, which
makes "exactly which commands are authorized" the security boundary of the feature.


U1. sudoers matches command arguments as ONE CONCATENATED STRING
    man sudoers, "Wildcards in command arguments":
      "%operator ALL = /bin/cat /var/log/messages*"
    also permits
      "sudo cat /var/log/messages /etc/shadow".
    So the obvious per-sandbox form `-a com.apple/yoloai*` ALSO permits
    `-a com.apple/yoloai -f /etc/pf.conf` — i.e. loading the main ruleset, which
    destroys vmnet NAT for every VM on the host. THE GLOB FORM IS UNSAFE.
    The man page's own remedy is an anchored regex, and it states the ToCToU and
    negation caveats "do not apply to rules where only the command line options are
    matched using a regular expression" — which is exactly this case (literal command
    path, regex arguments only). Regex arg matching needs sudo >= 1.9.10; we have 1.9.17.

U2. `visudo -c` CANNOT catch this — it validates syntax, not security
    All six candidates parsed OK, including the unsafe glob:
      exact literal args           parsed OK
      UNSAFE glob                  parsed OK
      anchored regex               parsed OK
      regex per-sandbox            parsed OK
      no args allowed ("")         parsed OK
      subcommand form              parsed OK
    CONSEQUENCE: the sudoers line must be GENERATED BY yoloai and verified by a permit/
    refuse matrix, never documented for users to hand-copy. A doc typo that widens the
    grant to passwordless root is indistinguishable from the correct line to every
    validation tool on the machine.

U3. sudoers cannot constrain STDIN, and `pfctl -a A -f -` reads its ruleset there
    The earlier harness (privileged.sh:75) loads rules with `-f -`. Whatever regex pins
    the argv, the RULE CONTENT is unconstrained by the authorization mechanism.

U4. The anchor parser ACCEPTS content far beyond "a block rule" (parse-only)
      pfctl -a com.apple/yoloai -n -f -   <<< each of:
        block drop out ...          exit 0   accepted
        pass all                    exit 0   accepted
        set skip on en0             exit 0   accepted   <-- would disable filtering
        set limit states 1          exit 0   accepted
        nat on en0 ... -> (en0)     exit 0   accepted
        rdr on en0 ... -> 127...    exit 0   accepted
        load anchor "x" from ...    exit 0   accepted
        include "/etc/pf.conf"      exit 0   accepted   <-- parse-time file read
        scrub in all                exit 0   accepted
        anchor "sub" { pass all }   exit 1   SYNTAX ERROR (the only rejection)
    `-n` proves the PARSER accepts these, NOT that pf honors them in anchor context.
    That distinction decides whether the `-f -` form is survivable at all, and it is
    the first thing pf_authz.sh measures (Q1/Q2). If `set skip` is honored from inside
    an anchor, a NOPASSWD grant for `-f -` is a host-wide firewall-disable grant wearing
    a per-sandbox costume.

U5. `pfctl -n -f -` DOES validate correctly while unprivileged
      valid rule       exit 0
      syntax garbage   exit 1   "stdin:1: syntax error"
      bad address      exit 1   "could not parse host specification"
      empty            exit 0
    So yoloai can verify a generated ruleset BEFORE spending a privileged call. Note it
    unconditionally prints the "Use of -f option, could result in flushing..." warning to
    stderr even on success; that must be filtered, not treated as failure.

U6. Everything real needs root, and the failure signal is clean
      /dev/pf                     crw------- root:wheel
      pfctl -s info               exit 1  "pfctl: /dev/pf: Permission denied"
      pfctl -a <anchor> -s rules  exit 1  "pfctl: /dev/pf: Permission denied"
    A capability probe can therefore distinguish "not authorized" from "pf absent"
    (command-not-found) without any privilege of its own.

U7. INSTRUMENTATION ERROR, corrected — the first reading of U5/U6 was wrong
    `pfctl ... | head -3; echo $?` reports HEAD's status, not pfctl's, so both probes
    initially read exit=0 and I recorded "exit code is useless for detecting failure".
    Re-run without the pipe gave the correct 0/1 results above. Same shape as A25
    (instrumentation swallowing the error it was built to detect). Every exit code in
    this file was re-measured with stdout/stderr to temp files and no pipeline.

U8. /sbin/pfctl is SIP-protected
      -r-xr-xr-x  1 root  wheel  restricted,compressed  /sbin/pfctl
      csrutil status: System Integrity Protection status: enabled.
    It cannot be replaced, even by root. Contrast U9.

U9. Authorizing a yoloai SUBCOMMAND is a passwordless-root hole on a default Mac
    The alternative to U3 was `NOPASSWD: /usr/local/bin/yoloai _pf-sync`, moving rule
    generation inside our own code so stdin is not attacker-controlled. Measured here:
      yoloai resolves to  /Users/karlstenerud/bin/yoloai -> the repo build
      /usr/local/bin      not writable
      /opt/homebrew/bin   WRITABLE by the invoking user   <-- Homebrew's Apple Silicon default
      ~/go/bin, ~/bin     WRITABLE by the invoking user
    A NOPASSWD grant on a binary any user process can overwrite IS passwordless root.
    QUALIFICATION: not reachable by the agent we are containing — the seatbelt profile is
    `(deny default)` with explicit subpath allows (profile.go:25), so a sandboxed agent
    cannot write those directories. It is reachable by anything else running as the user.
    Weaker than U8 by a wide margin. This option is dead unless the binary is installed
    root-owned into a non-user-writable prefix, which yoloai's copy-a-file install is
    specifically designed not to require.

U10. pf TABLES remove the stdin problem entirely  <-- the finding that changes the design
    `pfctl -T add|delete <address...>` takes addresses as ARGV, not stdin (man pfctl,
    -T command). So the split is:
      once, at setup:   load static rules referencing a table  (needs a real password)
      per sandbox:      pfctl -a <anchor> -t <table> -T add|delete <ip>
    The entire unattended argument surface becomes one IP address, which an anchored
    regex pins exactly:
      /sbin/pfctl ^-a com\.apple/yoloai -t yoloai_src -T (add|delete) [0-9.]+$
    No stdin, no file paths, no wildcards, on a SIP-protected binary (U8). Worst-case
    abuse of the grant is adding or removing addresses from yoloai's own table, which can
    only affect traffic yoloai's own static rules already match. It cannot disable pf,
    cannot touch the main ruleset, cannot install NAT or redirects.
    TRAP: `-T add -f <file>` is also legal (man pfctl), so the regex MUST exclude `-f`.
    The `[0-9.]+$` form above does; a `.*` form would not.
    BONUS: teardown becomes a table delete, so it needs no rule reload — and rebuilding
    membership from live-sandbox state makes a missed reap self-healing, which removes
    the reaper-child mechanism the sudo-wrapper model needed.

U11. Privilege dropping is mechanically available on darwin
      syscall.Setuid(1) -> EPERM (errno 1), Setgid(1) -> EPERM
    EPERM, not ENOTSUP: Go implements both on darwin and they would succeed as root.
    (Order matters: setgid before setuid, plus initgroups for supplementary groups.)

U12. ...but `sudo yoloai` strips the agent's credentials on macOS with no way back
    fileutil.SudoParentEnv (fileutil.go:47) recovers sudo-stripped vars by reading
    /proc/<ppid>/environ. Confirmed: `ls /proc` -> "No such file or directory". The
    recovery half of yoloai's sudo support is Linux-only by construction, so
    `sudo yoloai new` on a Mac hands the agent an environment with no ANTHROPIC_API_KEY
    or CLAUDE_CODE_OAUTH_TOKEN. Whether `sudo -E` is even permitted under this machine's
    sudoers (macOS defaults to env_reset) is measured by pf_authz.sh Q6.

U13. The earlier harness already used a SINGLE FIXED ANCHOR
    privileged.sh:40 — ANCHOR="com.apple/yoloai_spike", not one per sandbox. Combined
    with U10 that is the whole design: one fixed anchor, one fixed table set, static
    rules, per-sandbox membership. Every variable part moves out of the authorization
    surface and into table contents.


U14. The sandbox address does not exist at launch — there is an ENFORCEMENT WINDOW
    Any address-keyed design (U10's tables, or per-sandbox rules) can only be written
    once the address is known. It is not known at start: `tart ip` reads HOST-SIDE DHCP
    LEASE RECORDS (netcheck.go:82, and its own comment at :148 says so explicitly), and
    apple's address comes from `container inspect` status.networks[0].ipv4Address, also
    populated after the guest boots. So the ordering is forced:
        start guest -> wait for address -> add to table -> VERIFY present -> launch agent
    Only the last arrow is a security boundary. Boot traffic before the rule exists is
    unfiltered, which is acceptable only because no agent code has run yet. If the agent
    launch is ever reordered ahead of the table add, the guarantee is void and nothing
    about the sandbox looks different. This belongs in a test, not a comment.

U15. Address-keyed filtering FAILS OPEN if the address changes mid-run
    A `block from <table>` rule stops matching when a sandbox's address is no longer in
    the table, so a mid-run address change silently unfilters that sandbox. Two sub-cases,
    only the second of which is dangerous:
      (a) vmnet re-picks the subnet and the guest keeps its dead lease. The sandbox is
          stranded with no connectivity at all (DF172) — fail-closed by accident, and
          already detected by the SandboxNetHealth probers on both apple and tart.
      (b) the guest DHCP-renews into the NEW subnet. It regains connectivity with an
          address the table does not contain, i.e. fully unfiltered, and every health
          probe reports OK because the address genuinely is live.
    Whether (b) actually happens is measurable with the existing ../vmnet_switch.sh
    harness and has NOT been measured. The obvious structural fix — default-deny the
    whole vmnet subnet and pass per sandbox — is ruled out by the property the earlier
    research deliberately established: a second, non-yoloai VM on the same bridge must be
    unaffected. So (b) needs either a re-check loop or an explicit documented limit.
    This is the sharpest unresolved risk in the whole approach and it is NOT specific to
    the authorization question — it applies to per-sandbox anchors identically.
