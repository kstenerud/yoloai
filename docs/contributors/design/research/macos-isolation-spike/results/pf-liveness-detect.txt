== V3b FAULT F3 'CANNOT ASK' — the free negative, and the fault the canary used to miss ==
        The first detC read HEALTHY iff the probe returned HTTP 000, and the probe helper defaults to
        000 on every failure. So a dead container, a dead daemon or a down network all read HEALTHY —
        the detector reported sound for every fault except the one it was aimed at, which is a free
        negative wired into production verification. Both arms of it are induced below, and the OLD
        sentinel runs beside the new one on the same fault in the same run: a fix that is never
        measured against the defect it claims to close is a claim, not a result.

== V4 GRANT SURFACE — what each detector would cost at the security boundary ==
        The shipped D132 grant permits exactly four forms. Installing it here in its real shape (with
        this run's anchor root) and asking for each detector's command is the only way to know.
        grant installed and validated
        PERMITTED  detector C (none needed)           pfctl -s info
        PERMITTED  detector A wants                   pfctl -s rules
        PERMITTED  detector B wants                   pfctl -a com.apple/yoloai_v -vvs rules
        PERMITTED  (the permitted anchor read)        pfctl -a com.apple/yoloai_v -s rules
        
        So detector A needs a NEW grant line for the WHOLE main ruleset, and detector B needs the
        existing anchor read widened to -vv. Both are security-boundary changes: D132's permit/refuse
        matrix has to be re-run, not just a regex edited. Detector C needs nothing.

== WHAT WAS NOT TRIED ==
        - A third fault: pf DISABLED (`pfctl -d`). D132's check 1 already covers it and `-s info` is
          in the shipped grant, so it is the one state existing verification does see.
        - Shadowing by a real system service. `pass quick all` was injected by hand; no service was
          induced to insert its own anchor ahead of com.apple. The mechanism is pf.conf's own
          documented behaviour, but the specific trigger is not demonstrated here.
        - Detector cost under load. All timings are on an idle host with one guest.
        - Whether the canary can run concurrently with a real acquisition. It rides rule 1b's window,
          so two sandboxes starting at once share that window; not tested. This is not a gap that a
          better sentinel closes: the canary MUTATES LIVE POLICY (flush the allowlist, probe,
          restore) and so races every acquisition by construction. Anything adopting it needs the
          acquisition lock, or it needs a canary that does not write.
        - A fault DURING the canary's own window. If the host dies between `empty` and `populate`,
          the sandbox is left with an empty allowlist and no egress. The restore is not guarded.
        - Whether the two controls can themselves be fooled together. F3a and F3b each break the
          path in one place; a fault that makes the destination answer while pf is dead would
          satisfy both controls and the canary alike, and nothing here induces one.
