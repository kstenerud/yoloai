================================================================================
READING NOTES — what the numbers above mean, written at the run and not later
================================================================================

1. THE DIRECTION IS VIABLE AND THE MARGIN IS LARGE. 99.2% of what the agent
   emitted is HTTP(S) or DNS. A host-side proxy serves both. The threshold was
   fixed at 95% before the run so that the figure could not be read as whatever
   it turned out to be.

2. ZERO QUIC, AND THAT IS THE LOAD-BEARING NEGATIVE. UDP/443 is the one shape
   that looks like HTTPS in every summary and is not served by an HTTP CONNECT
   proxy. It is counted by its own kernel filter rather than inferred, because
   run 2's text-parsing predicate would have labelled it `tcp/443` and folded it
   into the proxyable bucket -- the single finding that could falsify the
   direction was the one that predicate could not express. Absence here is one
   agent on one network; Chrome-style clients and gRPC endpoints would answer
   differently, and nothing here says otherwise.

3. THE REMAINDER IS 26 FRAMES AND IT IS NOT ALL ALIKE. Seven are ARP, which
   never leaves the bridge and is irrelevant to a proxy -- so the honest
   proxy-relevant remainder is smaller than 0.7%. The other 19 are the finding:

4. SSH TO GITHUB, UNASKED. 19 frames to 140.82.121.4:22 (github.com), and to
   .3 in the voided run 2 -- so it reproduces across sessions and is not a
   fluke. The task asked for `npm init`, an npm install, and a LOCAL git commit.
   The repository has no remote and the host's ~/.gitconfig (which yoloAI mounts)
   contains no url.insteadOf rewrite, so neither obvious explanation holds. 19
   frames is a handshake and a teardown, not a transfer: something attempted
   GitHub over SSH, got no further than the version exchange, and the session
   still succeeded with exit 0.

   Two things follow. The session did not NEED it -- so a chokepoint that cannot
   carry SSH would not have broken this task. And an ordinary session reaches for
   SSH anyway, which means P3 is not a hypothetical about power users. What
   attempted it, and whether any task would fail without it, is NOT established
   here; a scouting run meant to separate task-driven from setup-driven SSH was
   abandoned rather than half-run, and the question moves to P3 where it can be
   asked with controls.

5. DNS IS 24 FRAMES TO 8.8.8.8, not to docker's embedded resolver. So the guest
   resolves externally today, and under a chokepoint that path disappears
   entirely -- which is P6's question, and prior-art section 1 (Cilium) already
   says the answer is to let the proxy resolve.
