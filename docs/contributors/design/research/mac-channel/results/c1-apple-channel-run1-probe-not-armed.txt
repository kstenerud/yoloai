does the apple backend expose a host<->guest data channel, and does it survive a guest with no IP stack?

  baseline: a guest reaches an external address: True   (default network, no flags — the positive control A22 requires)

  guest AF_VSOCK/CID probe: 'AF_VSOCK=ok | AF_UNIX=ok | AF_INET=ok | dev_vsock= True | local_cid= 3'   (the raw guest-side capability read, before any channel is asked for)

  AF_UNIX sun_path budget for the host end: 22   (108-byte limit; a host end under ~/.yoloai/sandboxes/<name>/ can exceed it, which bit this run before it was noticed)

-- expectations, rendered from the values above --
  [PASS] apple exposes a host<->guest channel that carries arbitrary bidirectional data  <- with --publish-socket, default network=True
  [PASS] that channel survives a guest with no IP stack, which is shape (B)  <- with --publish-socket, --network none=True
  [FAIL] --network none actually removes the guest's egress  <- under --network none=True

-- WHAT WAS NOT TRIED --
  - **the guest-initiated direction, beyond the vsock probe above.** `--publish-socket` is guest-listens/host-connects. An egress proxy wants the opposite, so a build on this needs either a guest-side shim that multiplexes local connections over the channel, or a host proxy that connects in and speaks a reverse protocol. Which of those is cheaper is a design question this run does not open
  - whether yoloAI can pass these flags at all. `runtime/apple` passes neither --network nor --publish-socket today; what it costs to thread them through is a code question (and the --network half is C3's defect)
  - the channel under the real image. This runs alpine+python3, not yoloai-base, whose entrypoint.py takes over PID 1 — so nothing here says the shim can be started before the agent, only that the host end exists from container start
  - throughput and latency. Every payload here is a few bytes; whether this channel carries a real HTTP session at usable speed is unmeasured and is P2's question one layer down
  - restart and lifecycle. Whether the host end survives a container stop/start, a daemon restart, or a reboot — the whole subject of enforcement-state-reaping.md — is untouched
  - SOCK_DGRAM, and anything other than a stream socket
  - n. One host, one macOS (26.5.1), container CLI 1.0.0, one boot per arm

`egress.sample("under --network none")` re-ran the *default network* arm and read True.
The arm was never measured. The `channel` probe above it had the identical defect,
caught in review before the run (D136 §3) and fixed with an ARM dict; the fix was not
carried to the second probe. Nothing about the world is in this row.

The two PASS rows are unaffected — `channel` was armed correctly, and its baseline and
samples came from the same callable across three genuinely different arms. They are
superseded by run 2 only because the run is re-rendered whole.
